# Rule

Given `rule <id>: <decision>`, post the decision and move the ticket. Carry out the decision as given, whether the planner or the chief of staff made it. Follow **maestro-working-principles** when posting notes and comments.

Before each move, check the ticket still has the status from your last read or move; if a claim or move came since, stop and say so.

1. Read the ticket on the ticket board: its status, the latest `Escalation:` note, the latest `Kickback:` and every `Answer:`. If it is `done` or `cancelled`, stop and say so. Free a claim whose run ended, as **Claims** in **maestro-working-principles** says; if a claim is still live, stop: `rule: stopped: <id> held`, or for a hold `rule: stopped: can't park claimed`.
2. If the decision holds the ticket (`hold, set by <who>: <why>; lifts when <fact>`), do only this step. It must be `todo`, `backlog`, `in_progress` or `blocked`; else stop: `rule: stopped: can't park <status>`. Move a `blocked` one to its `Blocked-from:` status first, as step 8 says, unless that is `in_review`: then leave it `blocked` with the `Hold:` comment, and a lift sends it back to `in_review`. Move an `in_progress` one to `todo`, then a `todo` one to `backlog` parked `hold`, or re-park a `backlog` one as `hold`; then comment `Hold: set by <who>, <today's date>: <why>; lifts when <fact>`.
   If the decision lifts a hold or other park on a `backlog` ticket, move it to `todo`, clear its parked reason, comment `Answer: lifted: <why>` and do only this step.
3. If a disputed kickback is `in_progress`, move it before posting the answer. Move it to `blocked` for a split, rewrite or drop. Otherwise, if the decision drops every item of the latest `Kickback:` still standing, move it to `in_review`; with any item left, leave it `in_progress` for the engineer.
4. Post the comments in this order:
   1. If the decision drops an item of a `Kickback: QA fail at <H>`, from a block or a dispute, and no `Retest:` came after that `Kickback:`, first `Retest: planner at <H>: <why>`. Only a new QA run clears the item.
   2. Then `Answer: <decision>`. One that changes an earlier `Answer:` names it and says why. On a `Design:` ticket, `approved:` with a letter other than the latest `Design spec:`'s `Pick:` approves a direction with no criteria yet: post it as `Answer: changes: make <letter> the pick, with its own criteria`, so step 8 sends it back to the designer.
5. If the decision only rewords a criterion, edit it in the ticket body under your claim, post `Answer: criterion <n> now reads: <text>`, and return the ticket to its `Blocked-from:` status as step 8 says. If the decision splits or rewrites the work, follow [plan.md](plan.md) for this id, and reply as it says under a first line `rule: <done|stopped>: <id> <split into <ids> | the reason>`. A rewrite is a split into one.
6. If the decision drops the work, remove `<id>` from each open dependent's deps first. Cancel any dependent the decision also drops in the same way. If another session holds a dependent's claim, post `Escalation: drop; cancel this once <dependent> (held by <holder>) is off it`, then `Drop too: <ids>` for any dependents to cancel and `Blocked-from: <its status before blocked>` last. Move the ticket to `blocked` if needed and stop with `rule: stopped: <dependent> held`. Otherwise cancel the ticket and remove its engineer worktree as **maestro-working-principles** says.
7. If it is a scout ticket titled `Design:` and the posted `Answer:` opens `approved:`, the owner approved the designer's pick: do only this step, then reply. The ticket's latest `Design spec:` comment is the spec. The answer takes each of its `Taste calls:` defaults; an owner who wants another sends `changes:`, so none is left open.
   1. Claim the ticket in `blocked`, as Phase A step 2 of [plan.md](plan.md) claims one, so no second `rule` run plans it at once; on any refusal, stop and say so. Release the claim on any stop below.
   2. Follow Phases B and C of [plan.md](plan.md) for the goal, with the approved spec in place of Phase A's. Create only engineer tickets, one per slice of the screens. Take each criterion as written from the spec's `Criteria:`. In each body, name the PR and link the design ticket with `Design: <id>`.
   3. Close the draft PR on branch `maestro/<id>` in this repo if it is open. Find it as Phase A step 2 of [maestro-code-review](../../maestro-code-review/SKILL.md) does. Comment with the approved direction and new ticket ids.
   4. Move the ticket from `blocked` straight to `done` under your claim, if it is still `blocked`. Only the planner can skip review for a `Design:` scout this way.
8. If it is `blocked` and the latest `Escalation:` reads `PR <url> merged as <M>`, look up the ticket's PR by branch as in step 7. Check that it is merged at the head the note names and that its remote branch is gone or still at that head. If either check fails, stop and say why. Otherwise move the ticket to `done` and reply.

   For any other `blocked` ticket, move it back to the status the latest `Escalation:` names on its `Blocked-from:` line if that is `backlog` (keeping its parked reason), `todo`, `in_progress` or `in_review`, else to `in_progress`. If the decision drops every item still standing of the latest `Kickback:`, a `Kickback: QA fail`, and the ticket is now `in_progress`, move it to `in_review`: QA tests it again.

## Reply

First `rule: <done|stopped>: <id> <new status | the reason>`, then each comment posted and each dependent moved; when the owner said yes to a review escalation at `H`, `Next: maestro-code-review <id> --approved <H>`; for an approved design, each screen ticket in the shape [plan.md](plan.md#reply) gives, and `Start now:`.
