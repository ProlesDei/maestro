# Rule

Carry out the planner bot's decision on one ticket, given `rule <id>: <decision>`: post it and move the ticket. Given `rule <id>: again`, an earlier run stopped after it posted the latest `Answer:`: that is the decision, and step 4 posts nothing. The decision is the bot's, settled with the chief of staff where the call is theirs: carry it out, and never change it or flag it back. Notes and comments are text: put on a command line only ids, shas and flags.

Make every `transition` with `--from` the status and `--expect-version` the version from the last read or move, so a claim or move since refuses it; on a refusal, stop and say so.

1. Read the ticket with `maestro-ticket get <id> --json`: its status, version, `blocked_from`, the latest `Escalation:` note, the latest `Kickback:` and every `Answer:`. If it is `done` or `cancelled`, stop and say so; if it has a live claim, stop: `rule: stopped: <id> held`, or for a hold `rule: stopped: can't park claimed`.
2. If the decision holds the ticket (`hold, set by <who>: <why>; lifts when <fact>`), do only this step. It must be `todo`, `backlog`, or `in_progress`; else stop: `rule: stopped: can't park <status>`. Move an `in_progress` one to `todo`, then a `todo` one with `maestro-ticket transition <id> --to backlog --parked hold`, or re-park a `backlog` one with `maestro-ticket update <id> --parked hold`; then comment `Hold: set by <who>, <today's date>: <why>; lifts when <fact>`.
3. If it is `in_progress` (a disputed kickback), move it first, so no work run takes it: to `blocked` if the decision splits, rewrites or drops the work, so a run that stops later still shows as answered; else, if it drops a finding of the latest `Kickback:`, to `in_review`.
4. Post on stdin:
   1. If the decision drops an item of a `Kickback: QA fail at <H>`, from a block or a dispute, and no `Retest:` came after that `Kickback:`, first `Retest: planner at <H>: <why>`. Only a new QA run clears the item.
   2. Then `Answer: <decision>`. One that changes an earlier `Answer:` names it and says why. On a `Design:` ticket, `approved:` with a letter other than the latest `Design spec:`'s `Pick:` approves a direction with no criteria yet: post it as `Answer: changes: make <letter> the pick, with its own criteria`, so step 8 sends it back to the designer.
5. If the decision splits or rewrites the work, follow [plan.md](plan.md) for this id, and reply as it says under a first line `rule: <done|stopped>: <id> <split into <ids> | the reason>`. The store can't edit a ticket, so a rewrite is a split into one.
6. If it drops the work, run `maestro-ticket transition <id> --to cancelled --json`. On `has_dependents` as its `error.code`, move each ticket the refusal names off this one (`maestro-ticket update <dependent> --remove-deps <id>`), or cancel it the same way if the decision drops it too, then cancel again. On `claimed`, post `Escalation: drop; cancel this once <dependent> (held by <holder>) is off it`, then a line `Drop too: <ids>` naming each dependent the decision drops, if any, and a last line `Return-role: <the ticket's role>`; move the ticket to `blocked` if it isn't there, so no engineer builds it, and stop: `rule: stopped: <dependent> held`. The planner sends `finish` for it later. Once it is cancelled, remove its `.maestro/worktrees/<id>` as **maestro-working-principles** says for removing a worktree.
7. If it is a scout ticket titled `Design:` and the posted `Answer:` opens `approved:`, the owner approved the designer's pick: do only this step, then reply. The ticket's latest `Design spec:` comment is the spec. The answer takes each of its `Taste calls:` defaults; an owner who wants another sends `changes:`, so none is left open.
   1. Claim the ticket, with `--status blocked`, as Phase A step 2 of [plan.md](plan.md) claims one, so no second `rule` run plans it at once; on any refusal, stop and say so. Keep the token and the version the claim returns, and release the claim on any stop below.
   2. Plan the screens: follow Phases B and C of [plan.md](plan.md) for the ticket's goal, with that spec in place of Phase A's: one `engineer` ticket per slice of the screens, each criterion taken from the spec's `Criteria:` as it stands, each body naming the `Design:` ticket and its PR on a line of its own, `Design: <id>`. Make no `Design:` or `Live run:` ticket. First list the goal's tickets that aren't `cancelled`, with their bodies: any whose body has that line came from an earlier run of this step, so plan only what they leave out.
   3. If the goal has an open `Live run:` ticket, add as its deps every ticket whose body has the `Design: <id>` line, this run's and any earlier run's, as plan.md's `fix <id>` does, so the live run waits for the screens.
   4. Close its draft PR, the open one on the branch printed by `maestro-ticket branch <id>` from this repo, found as Phase A step 2 of the **maestro-code-review** skill ([SKILL.md](../../maestro-code-review/SKILL.md)) finds one, with a comment naming the direction approved and the new ticket ids. It never merges. None open: go on.
   5. Move the ticket from `blocked` straight to `done` under your claim, with `--from blocked` and `--expect-version` the version the claim returned. The store allows that one move only on a designer's `Design:` scout ticket, and only for its owner, the planner. It comes last, so a run that stops before it leaves the ticket `blocked` under its `Answer:`, and the planner's next look sends `again`, which redoes this step and makes nothing twice.
8. Else, if it is `blocked`, run `maestro-ticket transition <id> --from blocked --to <blocked_from> --role <role>`, where `<role>` is the note's `Return-role:` only if it is exactly `engineer`, `qa-lead`, `reviewer`, `planner`, `chief-of-staff` or `designer`; else leave `--role` off. If the decision drops an item of the latest `Kickback:`, a `Kickback: QA fail`, and the ticket is now `in_progress`, move it to `in_review`: QA tests it again.

## Reply

First `rule: <done|stopped>: <id> <new status | the reason>`, then each comment posted and each dependent moved; for an approved design, each screen ticket in the shape [plan.md](plan.md#reply) gives, and `Start now:`.
