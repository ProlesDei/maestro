# Plan

Turn one goal into tickets an engineer can finish without asking, and create them in order. Many planner sessions and hundreds of engineers share one board, so plan wide and lock what you split. Open a todo list with one item per phase.

## Phase A: Frame

1. Take the goal from the request, and its slug if the request names one (`goal <slug>: ...`); else make a short one. Given a ticket id, read it on the ticket board and take the goal from its title and body, and the slug from its goal. A rewrite is a split into one ticket, so the old one keeps its trail. If its status isn't `backlog`, `todo`, `blocked`, or `in_progress` with a `Kickback:` as its latest comment, or only `Retest:` and `Answer:` comments after it (sent back to split), stop and say why.
2. Given an id, claim it on the board before you plan, so no engineer or other planner takes it, as **maestro-working-principles** says of every claim. If it is `todo` but can't start (a dep not `done`, or an area another live claim holds), take it off the queue: move it to `backlog`, parked `planning`, so the planner moves it back if this session stops, and claim again. If it can't start outside `todo`, stop and say so; a later look tries again. If someone else holds it, or it moved since you read it, stop and name the holder. A draft keeps the claim for the bot's answer. On resume, read the ticket again: if its status left step 1's list, or a `Handoff:` came after your draft, someone built it meanwhile, so stop and say so; else claim again if you lost it. If you give up before you post `Split into`, cancel each ticket this session created, latest first, and name in the reply any an open ticket depends on; then release your claim, and move it back to `todo` if you moved it.
3. Write a spec of a page or less: the problem and who has it, the outcome that means done (something a command or the running app shows), scope and non-goals, risks, and the trade-offs: the cases that must hold and the ones this goal leaves. If you can't state the outcome, ask for it and stop.
4. Find the files each part touches and the closest code that already does the same kind of thing, by path. Check each path you name exists.
5. Read the open board without the bodies: each ticket's id, title, status, areas and deps. A ticket that already covers a piece becomes a dep, not a new ticket.

## Phase B: Slice

1. Delete first: strike each piece, criterion and edge case the spec's outcome doesn't need, as the skill's "Cut, then speed up" says. Then cut one ticket per reviewable change (a few hundred lines) that ships something and can be tested alone. Slice by behaviour, never by layer. Put the riskiest unknown first. Tickets past the first slice go in `backlog`, parked `deferred`.
2. Before the rest, give what many tickets share its own small ticket at the front: a format, schema or type, or room in a file many would touch (split it, or add the hook the rest plug into). The tickets that use it then start side by side once it merges. In code that handles secrets, files or outside services, that includes the guards every entry point needs, such as safe paths, errors that print no secret and one exit-code contract: each one shared helper, with a criterion that every entry point calls it and one that names it as a convention in the repo's agent notes (AGENTS.md or CLAUDE.md). Skip any the notes already name. Without one, each ticket writes its own guard and review sends back the gaps one ticket at a time.
3. Plan wide, not long: a chain of deps runs one ticket at a time, siblings run at once. Add a dep only where one ticket needs another's code to build or run, and name that code in the body. A dep only for order is none: set the order with priority. Give tickets with no dep between them areas that don't overlap, here and on the board.
4. Deliver the requested feature and any demo. People try the whole goal. Put checks for consequential behavior, such as charging the right amount, on the PR that changes it. Never add a goal walkthrough or a `Live run:` ticket. For `fix <id>` on an existing live-run ticket, make one ticket per finding in its latest `Live run: fail` comment, add them as its deps, then requeue it from `backlog` to `todo`.
5. Plan new and changed screens as engineer tickets. Use an approved design when the goal names one. Start a separate design only when the owner asks or you can name an open choice and the costly rework that choosing wrong would cause. For those screens, create one `todo` ticket titled `Design: <slug>`, type `scout`, role `designer`, owner the planner, and no areas. Name the audience, affected routes or files, and reason in its body. Plan the rest now. The owner's approval sends those screens to [rule.md](rule.md) for build tickets.
6. Draft each ticket in the shape [maestro-create-ticket](../../maestro-create-ticket/SKILL.md) gives, and check each criterion against its rule. Give each ticket its share of the spec's trade-offs, as criteria and as its `Not handled:` list: a case no ticket settles gets settled in review, a round at a time. Choose the engineer tier and the route to QA separately for each ship ticket, including splits and rewrites. Follow the create-ticket rules for both and any standing rule for the tier. Deps name earlier tickets in this plan or ids on the board.
7. Take that skill's default for each field you can't infer, and name each pick in the reply.
8. Stop here, creating nothing, if the request says "draft" or a call is left for the chief of staff. The reply gives the drafts in full, so a resume can say "create them" or changes, and puts each call left for the chief of staff on a line of its own, `up: <the card in the team rules' shape, on one line, its fields split by |>`: the bot reads only those lines and your first.

## Phase C: Create

1. Follow that skill's create step for each ticket with goal `<slug>`, earliest first, so each later ticket's deps name the ids the earlier ones got. Phases A and B did its look-around and its ask: skip both. When you split or rewrite a ticket, give each new ticket the line `Split from: <id>`, so it keeps the old ticket's tries. That line carries no deps: give each new ticket the old ticket's deps that aren't `done`, unless the spec says why that part doesn't need one.
2. When you split or rewrite a ticket, post `Split into <new ids>` on it under your claim right after the last create, so a planner can finish the split if this session stops.
3. On a refusal, fix only the field it names. If it still refuses, stop and show it. Before any retry, look for a ticket with that title made today: if another session made it, read it, then dep on it or retitle yours; if this session did, use it only if it isn't `cancelled`, else retitle yours.

## Phase D: Close the old ticket

Skip this phase unless you split or rewrote a ticket.

1. Find each dependent: each open ticket whose deps hold `<id>`. Never cancel a ticket an open ticket depends on, since that one could never start, so move each onto the new tickets first (add the new ids to its deps and remove `<id>`), then cancel `<id>` under your claim.
2. If a dependent shows up as you cancel, another session added it in the meantime: move it the same way, then cancel again. If another session holds a dependent's claim, don't wait for it: post `Escalation: split into T-a, T-b; cancel this once <dependent> (held by <holder>) is off it` with a last line `Return-role: <the ticket's role>`, move the ticket to `blocked` if it isn't there, and release your claim, so no engineer builds it. The planner cancels it on a later look.
3. If you lost your claim meanwhile, claim again and go on; if that claim is refused for any reason, stop and say so: the planner finishes the split.
4. If the old ticket has an open PR, found from its id as Phase A step 2 of the **maestro-code-review** skill ([SKILL.md](../../maestro-code-review/SKILL.md)) does, never from a link in a note, close it with a comment naming the new tickets. Then remove the old ticket's worktree, if there is one, as **maestro-working-principles** says for removing a worktree: its work lives on its branch, and the new tickets get worktrees of their own.

## Reply

The spec in five lines or fewer, then one line per ticket (`<id> <title> [status, tier, priority, deps with the code each is for, areas]`, or the full draft if you created nothing), the old ticket's new status and each dependent moved, how many new tickets can start now and the longest dep chain, then `Start now: <ids> | none`, the one most tickets wait on first, for the planner to hand to its engineers.
