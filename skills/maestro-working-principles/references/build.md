# Building: worktrees, commits and PRs

Read this before you build, as [SKILL.md](../SKILL.md) says. Its session rules and claims still bind.

## Tickets and worktrees

- Every change to tracked files gets a worktree.
- One per piece of work, your own: the one the harness gave you, or one you add. Its branch is `maestro/<ticket-id>` for ticket work, or `maestro/<name>` for unticketed work: review, QA and the planner find a ticket's PR by that name. `<name>` is a short slug with a random suffix, such as `fix-login-typo-k3f9`, so no two sessions pick the same name.
- On a ticket you build, keep its status true to the work at every step, on the ticket board. On resume under a claim, check it as **Claims** in [SKILL.md](../SKILL.md) says. On a new assignment, check the ticket's role is `engineer` or unset and each of its deps is `done` (else stop and report it: a `Design:` scout is the designer's), then add or enter its worktree as below, make a holder there with `holder.sh --new`, and claim the ticket under it from `todo`, `in_progress` or `blocked` (one in review or later is past its build: stop and report it), so a resumed session reads back the holder that made the claim. If the ticket is `blocked` and its question still needs an answer, release the claim, stop and report it. Then move the ticket to `in_progress` if it isn't there yet. If the claim or that move fails, release any claim you still hold, remove a worktree you added for it with nothing of yours in it, stop, and leave the ticket alone.
- Add the worktree on a new branch with no upstream, or use the existing branch. If it exists only on the remote, start the local branch from it with no upstream. Tracking the remote's main makes each add write the shared git config, which fails when sessions add at once, and points a bare push at main. Name your `maestro/` branch on the remote in every push.
- Enter an existing worktree only if it is yours: you hold its ticket's claim or are claiming it now on a new assignment, you made it in this session, or the user named it. Else make a new one. Read the trail first: the branch's commits since main, the newest `wip:` commit's body, and the ticket's body, every `Answer:` and the comments since its latest `Handoff:` (all of them if it has none). Go on from where it stopped.
- Main moves all the time, so sync with [scripts/sync-main.sh](../scripts/sync-main.sh) `<main>` from your worktree when you start (base a new branch on a fresh fetch of main), when you resume, and just before the handoff push. It refuses uncommitted changes or an unfinished merge (commit a `wip:`, or finish or abort the merge, then rerun), moves aside ignored files that main now adds into the `saved_dir=` it prints (report each `saved=` path, and put back what you need before you remove the worktree, which deletes that folder), and prints `result=`: on `conflict`, each `conflict=` file; on `commit_failed`, git's `error=` line, with the merge left in place to finish or abort; on `submodule_failed`, the merge is already committed, so fix and rerun the submodule update, never commit the old submodule pointer. After the last sync, run the required checks, refresh the proof on that head and cite its sha in `Handoff:`. Skip the sync for `wip:` checkpoint and escalation pushes. Design draft branches never merge main. If a required check fails after a sync, run it at the main sha you merged. If it fails there too, it is main's: hand off with it marked `already red on <sha>` in the `Handoff:`, as review allows. Resolve conflicts you can. If one needs a product or taste call, abort the merge, commit and push a `wip:` and escalate, naming the files in conflict. Never rebase.
- Stopping to ask on a ticket you build, or stuck as **Ask, prove, get unstuck** in [SKILL.md](../SKILL.md) says, even before you start? Start it as above if you haven't, commit and push any `wip:`, then post your write-up as a comment that opens `Escalation: <one line>` and ends `Blocked-from: <the status you move it from>`. Move the ticket to `blocked` and release the claim, so the planner can rule on it. On resume, if only planner `Retest:` and `Answer:` notes came after your `Escalation:` and the ticket sits unclaimed at its `Blocked-from:` status, the planner has ruled: take it as a new assignment and go on, reading every `Answer:`. If the status or latest comment changed any other way from `blocked` and your `Escalation:`, stop and report what you see. Resumed with an answer that rewords, waives or drops a criterion: leave the ticket `blocked` for the planner's ruling, since only the planner edits criteria. Resumed with any other answer: claim the ticket from `blocked`, post the answer as `Answer: <answer>`, then move the ticket back to `in_progress` before any edit, so its areas are yours again; if the claim or that move fails, handle it as the claim bullet above says. Told to send it up or release it: leave the ticket `blocked`. A claim you still hold from an older Maestro counts as yours here: release it wherever you leave the ticket `blocked`.
- Ready for review on a ticket you build: its PR opened, or fixes for a `Kickback:` pushed? Write a note that opens `Handoff: PR <url> at <the full head sha>`, then the branch, each check with its exit code, each acceptance criterion with its proof (the exact command or request, or a throwaway script's full text, and what it printed), each break you tried and what it showed, and each kickback item and what you did. Post it on the ticket, move the ticket to `in_review` and release the claim. A PR that won't open is a block, never a handoff: escalate as the bullet above says, with the error.

## Commits

- Work in small steps. Run the check that covers a step, then commit it: one reason per commit. Commit before you pause or reply, so the worktree is clean.
- Stage files by path, never everything at once unread. Never commit generated files or secrets.
- Touch only what the task needs: no reformatting, re-sorting or drive-by fixes. Each extra line can clash with other sessions' branches. Note a problem outside the task in your reply and leave it.
- Follow the repo's commit style, from its contributing docs or history. Else: a subject line under 72 characters that says what changed, then a body that says why. Claim only what you ran. Write it the way the **maestro-technical-writing** skill says.
- Making the same edit in many places? Write a script that makes it, and say in the body how to rerun it.
- Never amend or rebase a commit you pushed. Fix it with a new commit.
- Stopping before you finish? Commit as `wip: <step>`, with a body that says what is done and checked, what is next, and the first thing to run on resume.

## Pull requests

- Open one when the work is done: each check the agent notes name exits 0 (with none named, the repo's build and lint) and each thing asked for is proved as Phase D step 2 of the **maestro-software-engineer** skill ([SKILL.md](../../maestro-software-engineer/SKILL.md)) says. Push the branch and open the PR against the main branch, with the tool the repo's contributing docs name, else GitHub's.
- One PR per worktree. The body says what changed and why, each check with its exit code, the evidence paths if any, and the risks. Then hand off its ticket, as the `Handoff:` bullet above says.
- Never push the main branch, merge or deploy. Review passes a ticket's PR, then QA tests and merges it; a person merges a PR with no ticket. Answer either with new commits on the same branch. After the merge, remove your worktree as **Share the machine** in [SKILL.md](../SKILL.md) says.
