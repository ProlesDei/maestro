# 0782 /maestro-work defaults: the bot id, picking the playbook, where it stops

- **Context:** `maestro-play run` needs `<role>/<job>` and `--bot`, and a user's session isn't a bot. Release at trust level 1 opens a PR for a human to merge, so "to merged" can't finish in one sitting. The engine isn't built yet (slice 1), so the command follows the CLI in 0700 A2 and `docs/runner.md`.
- **Choice:** `--bot` comes from the flag, else `$MAESTRO_BOT`, else `user`, so a human-driven run shows its holder as `user/<session>`. Playbooks are picked from a status table that copies the `intake:` headers. If the engine says the intake doesn't match, the headers win, and the command never edits the ticket to fit. An `ask` goes to the user and comes back with `resume --choice`. `blocked`, `refused`, `stopped` and `idle` all stop the command. At level 1 it stops when the PR is open; running it again after the merge lets the release run confirm it and set `done`. Its own loop guard stops when the same playbook ends with the same status twice in a row.
- **Alternatives:** Pass `--next` per role, which can pick a different ticket. Merge the PR from the session (the session rules forbid it). Wait in the session for the merge (it could hold a session open for days).
- **Why:** The command stays a thin driver. Every decision about the work is still made by a playbook, a gate or the user.
