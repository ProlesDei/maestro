# 0730 What a prompt template can read, and how it reads it safely

- **Context:** 0700 A3 shows `.ticket`, `.run`, `.steps`, `.project`, `.env`, `.retry` and `.limits`, and says templates run with `missingkey=error`. It also gives `baseline` and `draft-setup` a `mode:` and leaves the rest open. One template serves several playbooks (`build` serves seven), so it can't assume another step's id exists, and scheduled runs have no ticket.
- **Choice:** Templates also read `.step.id`, `.step.mode` (always set, `""` by default) and `.step.with`, a map of the step's `with:` values, each rendered as a template before the prompt. The engine always sets every key: `.ticket` is an empty map when the run has no ticket, `.run.branch` and `.run.worktree` are `""` when there are none, `.step.with` is a map even when empty, and every `.steps.<id>` record has `outcome`, `reply`, `summary`, `output_path` and `exit_code`. A key a template needs is read directly, so a step that doesn't pass it fails `render` and lint. A key it can do without is read with `index` (`{{with index .steps "checks"}}`), which returns nothing for a missing key. Each template opens with a `{{/* */}}` header with `mode:`, `with:` and `reply:` lines: its interface, and what lint can check a step against.
- **Alternatives:** Fixed step ids every playbook must use (couples seven playbooks to one template); a `mode:` per playbook name (0700 B3: never by playbook); pasting inputs into the prompt (the contract says the session reads them itself).
- **Why:** A missing required input fails before any tokens are spent, and an optional one never breaks a playbook that doesn't have it.
