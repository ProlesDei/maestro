# 0714 The engine judges replies and writes the escalation

- **Context:** 0700 A2 retries a reply that misses a field or evidence and builds the `block` note from `_escalate.md`, but doesn't say when fields are required or where the note's parts come from.
- **Choice:** Every reply needs `status` and `summary`. A `done` or `failed` reply needs every `out:` field and a `done` reply needs `evidence`; `blocked` and `partial` replies don't. `processes` must be `[{pid, command}]`. A miss is retried in the same session up to `retry.max` (default `.limits.retries`, else 1), then blocks. The escalation prompt runs once in the same session, except when `usage check` exited 2. The note is built by the engine from its reply in maestro-escalate's order, with `Stopped at`, `Where`, `Tries`, the skips, the run id and `Return-role:` (0436). It's posted with the run's lease, then the ticket moves with `--release`: to `blocked` for the owner role, to `blocked` with `--role chief-of-staff` for `to: chief-of-staff` (0750), or to `todo` with `--role <role>` for any other role, a hand-off (0740). `block.to` is a template, and a step's own `block:` wins. `Return-role:` is the ticket's role when the run took it. A ticket already `blocked` is forwarded by release only (0435).
- **Alternatives:** Let the escalation prompt post the note itself (a session writing with the run's token breaks 0710); require `out:` fields on every status (a blocked step has no commit to report).
- **Why:** The judgment stays in the prompt, the routing and the write are deterministic, and a run whose budget is gone still escalates without spending tokens.
