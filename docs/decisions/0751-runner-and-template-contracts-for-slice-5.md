# 0751 The runner replies, prompt modes and note lines the slice 5 playbooks rely on

- **Context:** The Planner, Chief of Staff and Ops playbooks gate on runner output and on other roles' notes, where the old skills read prose. Other slices own those files (0700 C), so this lists what they must provide at merge.
- **Choice:**
  - **Runner (slice 2, `docs/runner.md`):** these requests print JSON on stdout: `summary` (`next_seq`), `trust <id>` (`level`, `risk`, `merge` and `deploy` as booleans for this ticket's risk class, and `needs_user` for migrations, auth and payments), `pr status` (`state`, `merge_sha`), `open pr` (`url`), `housekeep` (`plan`, `items`, `snapshot_recent`; with `--apply`, `snapshot`), `memory scan` (`proposals`, `flagged`, `over_budget`), `logs --since` (`new_lines`, `due` for adopted changes due for measuring, `next_cursor`) and `evals` (`results`, task to `pass` or `fail`). Add a new read-only request, `head <id>`, for every role from trust level 1: the head sha of the ticket's `maestro/` branch, as `{sha}`. It replaces the `git log -1` that `maestro-check-release` ran. `play` with `--input <text>` is also allowed for the chief-of-staff (`recap` hands each answer to `handle-escalation`).
  - **Prompt templates (slice 3):** these templates and modes, with these reply fields: `investigate` (`goal`: outcome, constraints, areas, decided, above_authority; `escalation`: question, options, facts, sources, recommendation, within_authority); `plan` (`spec`: outcome, scope, non_goals, approach, risks, order; `infrastructure`: plan, in_repo, commands, check, smoke, rollback, production, cost, risk); `tickets` (`plan`, `report`, `escalation`: tickets with title, kind, type, role, priority, status, goal, criteria, pointers, and optionally areas, deps, after, constraints, playbook; `escalation` also gives comment); `feedback` (`report`: question, answer, findings, spot_checked, missing, recommended_work, author_role); `groom` (fixes with ticket, version, command, to, note, args; next_seq); `patterns` (`measure`: verdicts, tuning_reverts, other_reverts; `find`: pattern, count, evidence, change, expected_effect, measure, tasks); `propose` (`tuning`: commit, baseline, window; `proposal`: proposals with title, class, pattern, evidence, change, expected_effect, measure); `curate` (`proposals`, `flagged`: verdicts, changed; `budget`: archived, size_before, size_after, changed; `commit`: commit, files); `draft-setup` (`setup`: draft, sources, asks; `setup-answers`: draft, changed, asks; `dod`, `dod-answers`: draft, items or diff, and floor as booleans verification, review, merge_queue, investigation).
  - **Notes (slice 4):** QA's pass note has a `sha: <sha tested>` line. The reviewer's `Handoff: approved` has `review-family: <family>`. Engineers' handoff notes carry `author-role: <role>` next to `author-family:`, so a release can send a ticket back to its author.
- **Alternatives:** Have Ops parse prose with a prompt step (spends tokens on a comparison, against 0700 B); give Ops `worktree add` on ticket branches to read the head (a write request used for a read).
- **Why:** A gate can compare only fields it can name. With these, a release, housekeeping and the wake gates spend no tokens.
