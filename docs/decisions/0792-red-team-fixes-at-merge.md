# 0792 What the merge's red-team pass changed: trailers come only from playbooks, and each sha is tied

- **Context:** The red-team pass on `pb/int` reproduced 14 issues. Most share one root: gates trust a note's `sha:`, `author-family:` and approval lines, but a bot could post any comment through the runner's `ticket comment`, a reply's `commit` and an ask's `--text` went into notes with their newlines, and release never compared the sha review approved, QA passed and the pull request merged.
- **Choice:** A bot's own `ticket` request is read only; every write comes from a playbook run (`docs/runner.md`, team rules). The engine wants a reply's `commit` and `sha` to be one git sha, and stores ask text and `--input` on one line. Release lands only a pull request whose state is `merged`, with a merge sha, from the sha QA passed (`was_merged`); checks that review approved that same sha (`reviewed_sha`); needs a known author family; and counts only an `Approved by the user:` that ends `(for sha <the sha QA passed>)`, which handle-escalation now writes. The merge queue's wait also needs a merge sha. QA checks out and tests the sha in the reviewer's `Handoff: approved`, quoted, not the newest `sha:` line on the ticket.
- **Alternatives:** Check each comment's author in the store (`--actor` is self-declared, 0718); keep the facts in store fields instead of comment lines (a store schema change, for Phase 7 if the gates need more).
- **Why:** With bots unable to write and every value the engine writes kept to one line or one sha, a trailer line can only come from a playbook's own template, and each gate compares shas the runner or an earlier gate already checked.
