# 0710 maestro-play calls maestro-ticket itself and sends every other step to the runner

- **Context:** Slice 1 of 0700 builds `tools/maestro-play`. 0700 says each step is checked like any runner request, but the runner isn't built, and `ticket:` steps call `maestro-ticket`.
- **Choice:** `ticket:` steps exec `maestro-ticket` directly. The engine applies the runner's `ticket` row itself: it allows only `get`, `list`, `events`, `doctor`, `create`, `update`, `comment` and `transition`, adds the key, holder, token and actor role, and checks the stop file before every step. `run:` and prompt steps, `preflight`, `usage check` and `session start|resume|close` go to the runner as `<runner> --json --bot B --role R [--ticket T] [--run ID] <request>`, which does the allowlist and trust checks and replies with one JSON object. The engine refuses a `run:` request the role may not send before it sends it, and lint does the same check. Claim, heartbeat and release belong to the engine, never to a playbook.
- **Alternatives:** Send ticket calls through the runner as well (one more process per write, and the runner would have to pass holder and token through); have the engine call harnesses directly (it would bypass the runner's session rules and `maestro-usage run`).
- **Why:** The engine is the only writer of holder and token (0431 as narrowed by 0700 D1), and the runner stays the one place that launches sessions and checks trust. Nothing here depends on who started the run, so the wake loop can send `play run` itself if 0700 question 2 is approved.
