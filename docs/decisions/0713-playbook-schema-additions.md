# 0713 The engine takes slices 3, 4 and 5's schema additions, and how runs end

- **Context:** The 0700 example doesn't cover every playbook slices 4 and 5 convert, and those slices wrote down what they need while slice 1 built the engine: 0730 (template data), 0740 (engineers, review, QA) and 0750 (Planner, Chief of Staff, Ops). The runner's `play` reply (0721) has `state: done | blocked | waiting | idle`.
- **Choice:** `maestro-play` implements all of them under their names, and lint checks each. Intake: a list of entries, `role` (`any` for no filter), `type`, `owner`, `title`, `latest` and `body` next to the `unless_` ones; `run --ticket` checks only the status. Top level: `input`, `cursor`, `session: run`. Steps: `when: {if, reason}` or `reason:`, `with:` or `vars:` (one map, `.step.with` and `.step.vars`), `session: fresh`, `body:`, `each:`, a step-level `block:`. `done:` fields are templates, with `role`, `actor`, `log` and `to: keep`. Every step record has every common field. Data and functions are 0730's and 0750's, plus `.run.scratch_dir` (0740). `run --next` tries request, sent-back, then new-work; scheduled playbooks run only by name, when the bot says they're due, because nothing in the store says a duty is due. States and exits: done 0, failed 1, usage 2, blocked 3, lost 4, idle 5, waiting 6, stopped 7.
- **Alternatives:** Keep 0700's keys only and have slices 4 and 5 rewrite their playbooks (each addition replaces a judgment call); put routing in the bot (non-deterministic); run scheduled playbooks on every idle `--next` (housekeeping on every wake).
- **Why:** Each addition turns a choice the Markdown left to the bot into data the engine checks, and taking the slices' names keeps the merge to the one conflict in 0715.
