# 0721 The runner's `play` request, and skills named only from `use.yaml`

- **Context:** 0700 makes playbooks YAML runs of `maestro-play`, started through a new runner request, and takes skill names out of playbooks. `docs/runner.md` still had bots building every request and prompt, a `Naming a skill` row that named `maestro-claim`, and `.maestro/rules.md` installed in the repo. Question 2 of 0700 (should the wake loop start runs itself) isn't answered.
- **Choice:** Two rows: `play run` and `play resume` for every role, on its own role's playbooks only, from trust level 1; `play render` and `play lint` for operations-manager, which runs evals and the improvement loop. A "Playbook runs" section says each step the run sends passes the stop file and the allowlist like any request, `--next` returns `state: idle` with exit 0 when nothing matches, `ask` replies `state: waiting`, and the stop file keeps the run state for `play resume`. The caller is a bot or the wake loop, and `--bot` names the bot either way, so the contract works whichever way question 2 goes, and nothing depends on it. The skill row now shows `<name>` and only for skills listed in `skills/use.yaml` (global only, the default for 0700 D2 question 3). The rules come from `<maestro>/playbooks/rules.md` and are never installed. `<common>/runs/**` joins the session deny list, and `housekeep` removes finished run states.
- **Alternatives:** Letting `play` skip the per-step checks because the playbook was linted (a linted playbook can still name a request above the trust level the repo is at now); a `--next` with nothing to do failing with exit 5 like `claim --next` (bots would treat a quiet queue as a failure); giving `render` and `lint` to every role (only Ops changes playbooks).
- **Why:** The runner stays the one gate, so moving the steps into a script adds no new way past the allowlist. Keeping the caller out of the contract leaves question 2 for Paul without blocking the engine.
