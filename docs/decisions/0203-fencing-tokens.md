# 0203 Fencing tokens on every claim

- **Context:** F3. A session whose lease expired could still comment, and could transition once the new holder released. Re-claiming your own lease didn't change the version, so a leftover process of the same session looked current.
- **Choice:** Each ticket keeps `lease_token`, a counter that grows on every claim, including a holder re-claiming its own live lease, and is never reset by release. Every claim also bumps `version` and logs a `claimed` event (`renewed: true` on a re-claim). `Ticket.CheckFence` guards `transition` and `comment`: under a live claim, the writer must name the holder (else exit 4 `claimed`) and its current token (missing: exit 2 `invalid`; stale: exit 4 `lease_lost`). A writer that names a holder or token on a ticket with no live claim gets `lease_lost`, so a late session is fenced even after the new holder leaves. `release --token` is optional; with it, a stale token can't drop a newer lease. v1 live claims get token 1 (the schema v2 migration), so their sessions must re-claim to learn it.
- **Alternatives:** Use `version` as the fence (it changes on every transition, so a holder's own writes would fence it); require the token on release too (breaks repeatable cleanup when the token is gone); fence heartbeats now (track B owns heartbeat).
- **Why:** A per-claim number that only grows is the standard fence. It rejects exactly the late writer and nobody else. Heartbeat fencing is left to track B.
