# 0780 Paul's 18 harness skills, and where use.yaml names them

- **Context:** Paul listed 18 harness skills (`skills/maestro-<name>/SKILL.md`). They're for harness sessions and are separate from the bot personas. 0700 left `skills/` as his empty slot, and `use.yaml` names skills by template, never by playbook or role. The five role skills (planner, software engineer, chief of staff, QA lead, code review) had to be mapped "to roles" through templates.
- **Choice:** Each skill is a Claude draft for Paul to edit, marked by an HTML comment under its frontmatter. Each one works inside a playbook step (the step and `playbooks/rules.md` win) and in the user's own session. Mapping: `all`: working-principles. `plan`, `build`, `feedback`: software-engineer, because 3 of the 5 playbooks that use `plan` are an engineer's builds (the other two are the `infrastructure` and `spec` modes). `baseline`, `build`: tdd. `verify`: prove-complete and qa-lead. `review`: code-review. `tickets`, `groom`: planner. `draft-setup`: chief-of-staff, because setup-project and definition-of-done are its playbooks. `tickets`, `draft-setup`, `propose`: technical-writing. `bots` stays empty, because these are harness skills and the bots have personas. The other 9, plus the 2 workflow commands (0781), go under `commands` and are never put in a prompt.
- **Alternatives:** Key `prompts` by role. The engine looks up templates only, and 0700 B3 rules out role or playbook keys. Put the role skills under `bots.<role>`, which mixes harness skills into bot instructions, against Paul's split. Name pr-review in `review`: it's a ten-pass gate, too heavy for every review step, so code-review points to it instead.
- **Why:** Each template gets only the skills its step uses, so the cached prefix stays small. No playbook or persona names a skill, so `check.py`'s rule still holds.
