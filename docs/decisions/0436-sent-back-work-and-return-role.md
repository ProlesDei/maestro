# 0436 Every sent-back ticket has a queue; escalations record the role to return to

- **Context:** The red-team pass of the integration found tickets that stall. A plan ticket, an investigation, the verification guide or an infrastructure request back in `in_progress` was in no role's intake, or matched no playbook. An escalation's `--role` replaced the author's role with nothing recording it, so an unblocked ticket could leave every engineer's queue. A workflow proposal put its prefix only in the transition note, so the Chief of Staff's intake, which reads the latest comment, never saw it.
- **Choice:** `maestro-check-intake` lists `in_progress --role <role>` as sent-back work for the Planner, QA and Operations too. A sent-back ticket that no `sent-back` playbook takes resumes the playbook that claims it from `todo`, after Start (playbooks README). `maestro-escalate` writes `Return-role: <role>`, and whoever unblocks the ticket sets `--role` from it. `maestro-propose-change` posts an `Escalation (chief-of-staff):` comment before blocking, numbers its idempotency keys per proposal, and spells out every write.
- **Alternatives:** A `sent-back` playbook per role (four near-copies of the later steps); have the store keep the pre-block role next to `blocked_from` (a schema change; the note already carries the escalation).
- **Why:** Every status a playbook can leave a ticket in has someone who picks it up, with docs changes only.
