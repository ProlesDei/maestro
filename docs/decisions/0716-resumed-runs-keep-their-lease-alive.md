# 0716 A resumed run starts its own keepalive, and one process drives a run at a time

- **Context:** The slice 1 review found two gaps in 0712. `claim --keepalive` ties heartbeats to the engine process that claimed, so after a crash, a stop or an `ask` the resumed run held its lease for one heartbeat (30m) and then lost it. And a run another process was still driving looked crashed on disk (`running`), so a second `--next` for the same bot resumed it with the same holder and token, and both would send the remaining steps, `merge` and `deploy` included.
- **Choice:** After the resume heartbeat succeeds, the engine starts `maestro-ticket keepalive <id> --holder --token --pid <its own pid>` in the background (ship/wave2's CLI). A process holds an flock on `<common>/runs/<run-id>.d/lock` while it drives a run, from the first save of a new run and before a resume reads the state. `resume` of a locked run fails, and `--next` passes over it. 0712's heartbeat-first resume is unchanged.
- **Alternatives:** Always re-claim with `--keepalive` (a new token, so every replay hits `idempotency_conflict`, which 0712 avoided); record the engine's pid in the state and check it (pids are reused, and a check then a write races); have the runner allow one `play` per bot (the wake loop and the bot would both need to go through the same runner instance).
- **Why:** The lease lives exactly as long as the process doing the work, and the run state has one writer, so no write or request is sent twice.
