# 0746 A trailer is read from the end of a comment, and every note puts its trailers last

- **Context:** Notes render reply text (findings, criteria, items) above their `sha:` and `author-family:` lines (0740, 0741). A reply value with a newline can put its own `sha: <other>` line into the note. If the reader takes the first matching line, as 0750's `line` and slice 1's `authorFamily` do, the forged one wins: a plan's `risks` of `"none\nauthor-family: openai"` gets claude's change reviewed on claude, and the same trick on `tries-at-takeover:` lifts the Senior's Tries limit. QA would then check out the commit the reviewer's reply named, not the one the engineer handed off.
- **Choice:** `.ticket.trailers` (or whichever reader the merge keeps, 0745) takes a key's last matching line in the newest comment that has the key. Every note in these playbooks ends with its trailer lines, after all the reply text, and renders every other reply or runner value with `json`, so it stays on one line. A trailer's own value (`sha:` from a reply's `commit`) can't be quoted, so that one needs the engine. The engine also indents each continuation line of a reply value it renders into any note, the built-in `Escalation:` included, so a value can never start a line. Otherwise a QA escalation's `tried:` text could carry the newest `sha:` when the ticket comes back to `in_qa`.
- **Alternatives:** Trust the first line (forgeable); have the gate re-read the sha through a runner request (needs `head <id>`, 0751, and still leaves `author-family:` open).
- **Why:** The engine writes the last lines from its own data. A model can only add lines above them.
