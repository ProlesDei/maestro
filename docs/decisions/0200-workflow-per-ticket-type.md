# 0200 Workflow per ticket type, blocked returns to its origin

- **Context:** F1 and F5. Blocked could move to any status, so review and QA could be skipped. There was no ticket type, no backlog and no tries. 0008 adds backlog and keeps cancelled; 0009 says scouts end at in_review.
- **Choice:** The store keeps one move table per type in `ticket/ticket.go`. Ship: backlog → todo → in_progress → in_review → in_qa → ready_to_release → done. Scout: backlog → todo → in_progress → in_review → done. Both allow the send-backs to in_progress, in_progress → todo (escalation) and todo → backlog. `in_progress → done` is gone for ship tickets. Every non-terminal status can be blocked (backlog too, so dependencies can block it) and cancelled. Moving into blocked stores `blocked_from`; blocked can then go only back there or to cancelled. A ticket created blocked returns to todo. Backlog is never handed out by `claim --next` (exit 2 if asked), only claimed by id. Type defaults to ship.
- **Alternatives:** Let blocked return to any earlier status (still lets a ticket blocked in review go back to in_progress and loop, but is harmless; rejected because the audit asked for exact return); keep `in_progress → done` for tracking tickets (scouts now cover that).
- **Why:** The workflow is the gate a confused session can't skip. Storing the origin is one column and makes the rule exact.
