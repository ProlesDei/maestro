# 0720 `list --latest-prefix` and `--not-latest-prefix`, filtered in the CLI

- **Context:** 0700 replaces `maestro-check-intake` with playbook `intake:` headers that the engine matches. Intake needs "blocked tickets whose latest comment starts `Escalation:`" and, for `unless_latest`, the opposite. Before this, the bot read up to 5 tickets with `get` and compared by hand. Slice 2 owns `cli/` and `sqlitestore/` but not `ticket/`, where `ListFilter` lives.
- **Choice:** `list --latest-prefix P` keeps tickets whose latest comment (highest comment id) starts with `P`; `--not-latest-prefix P` keeps tickets with no comment or whose latest doesn't start with `P`. The match is a case-sensitive byte prefix of the body, so `Escalation:` doesn't match `Escalation (chief-of-staff):`. `--limit` counts after the filter. The CLI does the filtering: it calls `Store.List` without a limit, then `Store.Get` for each ticket, so it works on any driver. The order stays priority, then numeric id, the same as `claim --next`, and is now documented and tested as part of the contract.
- **Alternatives:** A `LatestPrefix` field on `ticket.ListFilter` with a SQL subquery (one snapshot, one query, but it edits `ticket/`, which another slice's merge may touch); only the positive flag, with the engine subtracting two lists (two calls and a race between them); printing each ticket's latest comment in `list --json` (changes the output of every list).
- **Why:** It stays inside the files slice 2 owns and needs no schema change. Boards are tens to hundreds of tickets, so one `get` per listed ticket is cheap. The list and the reads aren't one snapshot, but intake is advisory: the claim and `transition --from` that follow are the real checks. If list volume grows, move the filter into `ListFilter` and SQL; the flags don't change.
