# 0717 A step can't set the flags the engine owns; a request intake with no status isn't a queue

- **Context:** The slice 1 red-team pass showed that a reply value rendered unquoted into a `ticket:` line (0715 renders, then splits) became flags: `-holder=`/`-token=` in Go's one-dash form passed the engine's check and wrote on another bot's lease, and a step's own `--actor-role` let a reviewer's reply set a ship ticket `done` as operations-manager. The same review found that `--next` listed every unclaimed ticket of the role for a `request` intake with no `status`, so the Chief of Staff ran `definition-of-done` on whatever ticket sorted first, and that `--ticket 1` (which the store reads as `T-1`) made `.ticket.id` differ from the run's ticket, so its writes went out without the lease.
- **Choice:** A `ticket:` step may not set `--json`, `--holder`, `--token`, `--idempotency-key`, `--actor-role`, `--store` or `--body-file`, and a `run:` step may not set `--json`, `--bot`, `--role`, `--ticket` or `--run`, in either dash form; lint checks the literal words and the engine checks the rendered ones. The actor role is always the run's role. `--next` skips intake entries with no status: they are a user's requests, run by name like scheduled ones. After its first read a run uses the store's ticket id. Quoting reply values stays the playbooks' job (0755).
- **Alternatives:** Quote every template action in a line automatically (breaks `join` spreading a list, 0715); lint every unquoted reply value (heuristic, and the engine guard covers the flags that matter); keep a step's `--actor-role` for scouts (0433 closes a scout with `--actor`, which stays allowed).
- **Why:** Whatever a reply says, it can't name another lease, another store or another role, and a quiet queue never runs the wrong playbook.
