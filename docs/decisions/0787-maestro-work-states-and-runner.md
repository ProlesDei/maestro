# 0787 /maestro-work: every run state, the runner it needs, and a routing table that matches intake

- **Context:** 0782 lists `done`, `waiting`, `blocked`, `refused`, `stopped` and `idle`. Slice 1's CLI (0713) also exits 1 (failed), 2 (usage or budget) and 4 (lease lost), and the command said to resume after any crash, a lost lease included. Its table sent infrastructure requests, `Plan:` scouts and verification guides to `senior-software-engineer/build-ticket`. A scout back at `in_review` went to `code-reviewer/review-change`. The engine refuses those on intake, but the fallback then left the session to choose from the headers. Every playbook's `run:` steps need the runner, and `maestro-play` finds playbooks through `$MAESTRO_PLAYBOOKS`, because they're never installed in the target repo. The runner contract (slice 2) also says `play`'s `<role>` must be the caller's role, which a user's session with `--bot user` isn't.
- **Choice:** The command stops on failed and usage with the run's `reason`. On lease lost it stops and never resumes that run. It resumes once only when there's no JSON state at all. It checks for the runner and `$MAESTRO_PLAYBOOKS` before the first run. The table gets rows, in intake order, for `Plan: ` titles, `operations-manager` and `qa-lead` tickets, and a stop for an investigation at `in_review`. **Merge follow-up for slice 2 (`docs/runner.md`):** a `play` request with `--bot user` comes from the human and may run any role's playbook. Each of its steps is checked against that playbook role's allowlist and the trust level, like a bot's. `user` is the human only when no run is the caller: the runner refuses `play` from any session a run started (the engine marks its sessions, for example with `MAESTRO_RUN_ID` in their environment). Then a ticket that says "run `maestro-play`" can't start a playbook from inside a step. `playbooks/rules.md` also tells sessions never to run `maestro-play`.
- **Alternatives:** One bot id per role from the user's session (then the user needs a bot for every role just to drive one ticket); calling the engine without the runner (`run:` steps have nowhere to go).
- **Why:** The command stays a thin driver, and it never retries past a stop the engine reports. The user can already start any playbook by hand. Checking each step against the playbook's role keeps the trust gates where they are.
