# 0725 The `play` reply passes the engine's exit code through; a run belongs to the bot that started it

- **Context:** The slice 2 review compared `docs/runner.md` with the engine on `pb/s1`. 0721 had `--next` with nothing to do exit 0, but the engine exits 5 for `idle`, and has three more states: `lost` (4), `failed` (1) and `stopped` (7). The `play run` row needed `--ticket` or `--next`, so scheduled playbooks with no ticket couldn't be sent. The engine's `resume` takes no `--bot` and trusts the run state, so nothing stopped one bot from resuming, or answering the `ask` of, another bot's run, whose holder and allowlist it would then use. And the engine runs `ticket:` steps itself (0710 on `pb/s1`), not through the runner.
- **Choice:** This replaces 0721's exit 0 for `idle`. `exit_code` and `run.state` are `maestro-play`'s, passed through. `status` is `ok` for `done`, `blocked`, `waiting` and `idle`, `failed` for `failed` and `lost`, and `stopped` for `stopped`. `play run` takes `<role>/<job>` with or without `--ticket`, or `<role>[/<job>] --next`. The runner refuses a `--bot` that isn't the caller (the wake loop counts as the bot it runs for), and refuses `play resume` unless the run state's bot is the caller. `ticket:` steps are documented as run by the engine under the `ticket` row and the stop file.
- **Alternatives:** Have the engine exit 0 for `idle` (an engine change outside slice 2, and the runner would still need a mapping for `blocked` and `waiting`); a `--bot` flag on `resume` checked by the engine (the runner is the one gate, and only it knows the caller).
- **Why:** Bots read `status` and `run.state`, so a quiet queue or an escalation is never a failure, and the exit codes stay in one place, the engine's README. Checking the caller in the runner closes the only way one bot could act through another's run.
