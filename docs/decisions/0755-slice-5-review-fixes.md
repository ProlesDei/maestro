# 0755 What the slice 5 review changed in the Planner, Chief of Staff and Ops playbooks

- **Context:** The review of slice 5 linted the 16 playbooks with slice 1's `maestro-play` (its working tree, which takes the 0750 keys) against slice 3's templates, and traced each path against 0750 to 0752. Several paths ended `done` without the work. Some reply values could add flags to a command line. Some gates couldn't render `true` or `false`. One nested run waited on an `ask` that nobody would answer.
- **Choice:**
  - **No nested runs.** `recap` posts each answer on its ticket as `Escalation (chief-of-staff): the user answered: <answer>`, and `handle-escalation` takes it on the Chief of Staff's next run. This replaces 0752's "`recap` does it through `play`" and 0751's `play --input` for the Chief of Staff. `handle-escalation` keeps `input: optional` for a user who starts it directly.
  - **One prefix for the user's approval.** `handle-escalation` writes `Approved by the user:` only when the user answered, and `Approved:` otherwise. Release's deploy gate for migrations, auth and payments reads only `Approved by the user:`, and checks it before `merge`. The Chief of Staff's handoff starts `Handoff: the Chief of Staff approved it`, never `Handoff: approved`, which is the reviewer's.
  - **No free flags.** Every reply or trailer value in a `ticket:` or `run:` line goes through `quote`. Groom's fixes name their flags (`from`; `add_deps`, `remove_deps`, `areas`) instead of 0751's `args`, and grooming has no `create`. Its notes and comments start `Groom: `, so a reply can't post another role's prefix.
  - **Gates print `true` or `false`.** `or` and `and` return an operand, so a gate or `when:` that combines lists is wrapped in `{{if …}}true{{else}}false{{end}}`. A reply flag is compared as `eq (print …) "true"`, so the string `"false"` never passes.
  - **Release:** a failed check on main always blocks. Before, at trust 2 and 3, it skipped `roll_back` and fell through to `done`. Each environment deploys, then smokes, in order, and the first failure stops the rest. Only environments a deploy started on roll back. `pr_state` runs only while the newest `Handoff:` is the `PR opened` one, so a closed pull request doesn't block the ticket after rework.
  - **Infrastructure request:** the plan runs unless an `Approved` note follows the latest plan note. Before, a ticket with no comments skipped its plan and closed itself, and an approved one re-planned forever. `check` and `smoke` come from the plan note.
  - **Answers reach the prompt.** The steps that apply an `ask` answer pass it as `with: {answers}` (draft-setup) or `with: {answer}` (tickets, in `answer-escalation`).
  - **Intake `role: any`** (slice 1's 0713) on `accept-report`, `handle-escalation` and `release`, since those tickets keep the investigator's, owner's or author's role.
  - **ship/wave2:** grooming also wakes when doctor's `leases` check counts an expired lease, and the cursor is the store's `next_seq`, never the reply's.
- **Alternatives:** Run `handle-escalation` from inside `recap` and answer its `ask` there (two paused runs and two leases, which 0752 itself rejects); match `Approved:` and trust its text (the Planner writes `Approved:` too); keep `args` and gate on its words (no template can parse flags safely).
- **Why:** Each fix closes a path where a model's reply, or a missing comment, decided a write the playbook meant to decide itself.
