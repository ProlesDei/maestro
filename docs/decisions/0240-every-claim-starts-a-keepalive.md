# 0240 Every claim in a skill starts a keepalive, and the check enforces it

- **Context:** Track B gave `claim` a `--keepalive PID` flag and made `heartbeat` and `release` need `--token` (0221, 0229). The skills already said "never run `maestro-ticket heartbeat`, the claim keeps the lease alive", but no claim command passed `--keepalive`, so nothing heartbeated and a long step would lose its lease. 0239 item 1 asked whether `$PPID` in a harness's shell is the long-lived session process.
- **Choice:** Both claim commands in `maestro-claim`, and the short claim in `maestro-propose-change`, pass `--keepalive $PPID`. Exit `2` on that flag means `$PPID` isn't a live process: the claim fails rather than run without a heartbeat. `evals/check.py` now fails on a `claim` without `--holder` and `--keepalive`; a `release` or `keepalive` without `--holder` and `--token`, even on a line about unheld tickets; any `heartbeat` command outside a "Never" line; and `comment --expect-version`, a flag `comment` doesn't have. VERIFIED on this box (Claude Code 2.1.x, 2026-10-29): `$PPID` in a Bash-tool shell is the `claude -p` process. UNVERIFIED for Grok Build and Codex; check before their first claim.
- **Alternatives:** Leave the claim without a keepalive and long TTLs (a dead session would hold its ticket for the whole TTL); have the bot runtime start the keepalive (it doesn't know the token until the claim's JSON is parsed, and the harness owns the claim).
- **Why:** The claim is the one step that knows the token and runs inside the session, so it is the right place to tie the lease to the session's life.
