# 0229 Heartbeats from a keepalive process tied to the session's pid

- **Context:** The brief: heartbeats come from a background process started by the claim, never from LLM turns, since one harness step can outlast a lease. Skills told sessions to run `heartbeat` themselves (G4.2). A background process also needs a way to know the session died, or it would keep a dead session's lease alive forever.
- **Choice:** `keepalive <id> --holder H --token N --pid PID [--ttl 30m] [--every ttl/3]` heartbeats the lease while process PID exists, checking the pid every second. It exits 0 when PID is gone (the lease then expires and is reaped, 0220) or on SIGINT/SIGTERM, and exits 4 when a heartbeat says `lease_lost`, which is how release, a terminal move or a re-claim stop it. Other heartbeat errors are retried within 5s. `claim --keepalive PID` starts one as a detached process (own session, no output) with the claim's holder, token, TTL and store; if it can't start, the claim is released and the command fails. PID is the harness session's process: in a Claude Code Bash call, `$PPID` (to verify per harness, 0239).
- **Alternatives:** A long-lived per-host daemon heartbeating every claim (one more thing to supervise, and it can't tell which session died); watching a file the session touches (needs LLM turns again); the claim command staying in the foreground (blocks the harness's shell).
- **Why:** A pid is the cheapest liveness signal the OS gives for free. The keepalive stops on its own in every ending: session dead, lease released, lease taken.
