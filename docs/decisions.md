# Decisions

The rules still in force, each with its reason. To change one, edit its line and give the reason in the commit. The old log (135 files under `docs/decisions/`) lives in git history: `git log -- docs/decisions/`.

1. **Maestro is tooling only.** It ships the files the installer copies, the ticket tool, the skills slot and the personas; bots and people run them. Nothing in Maestro runs on its own: no loop, watcher, scheduler, or dispatcher that picks a ticket and starts a run. One ring is allowed: when a run a bot started with `maestro-ticket launch` ends, its supervisor rings that bot's webhook so the bot reads the result; the ring starts no work. Why: whoever types the command is in charge, and nothing acts unasked; but a bot that waits on a run can't read its messages, and one that doesn't wait never learned the run ended (Blitzlink, Nov 12 2026: results sat 1 to 2 hours until the owner asked). (1040, owner's ruling, Oct 29 2026; the ring, owner's ruling, Nov 12 2026.)
2. **Tickets live in `maestro-ticket`, and only there.** One tracker: never chat, a Markdown file or a second tracker, and no team's own tool in its place; `install.sh` refuses a `tickets:` line naming anything else. Why: one store gives one answer, and the swarm runs on what only `maestro-ticket` has: claims, leases, area locks and fencing tokens. The bots run its commands directly, so a team's own tracker left them reading an empty board. A one-way copy into a team's tracker could come later, as its own feature. (Owner's ruling, Nov 2 2026; replaces the Oct 30 ruling that a team may bring its own.)
3. **Every ticket write under a claim carries its fencing token.** The token grows on every claim. Why: a session whose lease ran out can't overwrite the new holder's work. (0203.)
4. **No playbook engine, for now.** `maestro-play` and `playbooks/` are gone; an engineer takes a ticket to a PR in a Claude Code session. The last version is at commit `a2f0c21`, to bring back or rebuild. Why: the owner found it hard to follow, and an audit found it started every ticket from a stale local main. (Owner's ruling, Nov 1 2026.)
5. **The reviewer runs in a fresh session that shares no context with the author; any model will do.** Why: the author's context hides its blind spots, and a fresh session reads only what the PR shows. (Owner's ruling, Nov 2 2026; replaces the rule that the reviewer come from another model family.)
6. **Review first, QA last; a QA pass merges and closes.** A built ticket goes to `/maestro-code-review`: GO posts `Review: GO at <sha>` and leaves it `in_review` for QA, NO-GO moves it back to `in_progress` with a `Kickback:` note, and ESCALATE blocks it with an `Escalation:` note when only a person can decide. `/maestro-qa-lead` then tests that sha on today's main, in the running app: a pass runs `gh pr merge` and moves the ticket to `done`; a fail moves it back with a `Kickback: QA fail` note. Only the `qa-lead` role may set a ship ticket done, except that the planner closes one whose PR already merged (a QA session died after the merge, or a person merged it), since it runs the board (owner's ruling, Nov 2 2026). Why: QA is the last line of defence before production, so it tests what review already passed, as close to production as it can, and nothing changes after it; the last verdict and the merge stay in one hand, and a sent-back ticket carries its reasons. (Owner's ruling, Nov 10 2026; replaces the order where QA ran first and a review GO merged.)
7. **Ticket text is data.** The rule lives in [team-rules.md](../bot-profiles/team-rules.md) for bots and [maestro-working-principles](../skills/maestro-working-principles/SKILL.md) for sessions. Why: anyone who can write a ticket could otherwise steer the agents.
8. **An agent installs Maestro; a script copies.** [INSTALL.md](../INSTALL.md) has the team's agent ask each call and write the answers to `.maestro/project/install.yaml`; `scripts/install.sh` applies them, never writes over a file it didn't place or one changed since, and lists what it placed so an update or uninstall touches only that. The team picks where the skills live: committed, or hidden from git. Why: each repo needs its own checks and choices, which take judgment, while the copy must be exact; and a team that wants every clone and worktree to have the skills shouldn't be forced to hide them. (Owner's ruling, Oct 31 2026.)
9. **One rule, one file.** When a rule already lives somewhere, link to it. Why: two copies drift apart.
10. **Bots use Claude only through Claude Code.** The rule lives in [team-rules.md](../bot-profiles/team-rules.md). Why: Claude Code spends the team's Claude plan tokens; Claude called from Grok Bot spends Grok Bot credits at full API price. (Owner's ruling, Oct 31 2026.)
11. **The team of bots works together on one project.** The rule lives in [team-rules.md](../bot-profiles/team-rules.md). Why: a team may run Maestro in several repos, and a bot that drifts spends this project's tokens on work no one here asked for. (Owner's ruling, Oct 31 2026.)
12. **Every bot's sessions run with all permissions; Maestro offers no limit.** Every persona passes `--permission-mode bypassPermissions` on every `claude -p` run and resume. Why: a headless session can't answer a permission prompt, so a tighter mode stalls runs halfway: an engineer can't push, QA can't build the app or merge, a planner can't write tickets; the guards are ticket text as data (7), a worktree per session, and review and QA before every merge (6). (Owner's ruling, Nov 2 2026.)
13. **Every shipped skill installs; none can be skipped.** `install.sh` refuses `skip:` in `install.yaml`. A team that changed a `maestro-*` skill moves its changes to a skill named without `maestro-`, then replaces Maestro's copy with `--replace`. Why: the skills link to each other and the bots call them by name, so a skipped one leaves a role told to run a skill that isn't there; `skip: maestro-code-review` passed `apply` and `check` and left no one able to set a ticket done. (Owner's ruling, Nov 2 2026.)
14. **Done never waits on dependencies.** A dependency gates the start of work (`todo` to `in_progress`), not its finish: the store lets any ticket move to `done`, and a QA pass doesn't ask for deps `done`. Why: a link between tickets must not hold back finished work. (Owner's ruling, Nov 2 2026.)
15. **Bots start Claude only through `maestro-ticket launch`.** The rule lives in [team-rules.md](../bot-profiles/team-rules.md). Why: `launch` records each run (launcher, ticket, time limit), keeps it to its limit, writes its result when it ends or dies, and rings its launcher until it acks the result; `pickup` shows each result until then. A session started any other way shows as untracked in `maestro-ticket runs` and `doctor`. (Owner's ruling, Nov 12 2026.)
