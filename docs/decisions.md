# Decisions

The rules still in force, each with its reason. To change one, edit its line and give the reason in the commit. The old log (135 files under `docs/decisions/`) lives in git history: `git log -- docs/decisions/`.

1. **Work starts from a request, a run outcome or recovery.** Code serves the planner and the five delivery roles with no setup, and wakes the chief of staff's T3 thread with a fixed prompt. The relay records each handoff. A planner wake takes the renewable board lease and asks a judge only when the board needs a decision. After a reboot, the first `maestro-ticket cos` or `chief` command runs recovery itself; a known reset and a store reconnect trigger it too. Why: one runtime, run by code, needs no webhook, routine or service a person must set up. (Owner's ruling, Nov 20 2026.)
2. **Tickets live in `maestro-ticket`, and only there.** One tracker: never chat, a Markdown file or a second tracker, and no team's own tool in its place; `install.sh` refuses a `tickets:` line naming anything else. Why: one store gives one answer, and the swarm runs on what only `maestro-ticket` has: claims, leases, area locks and fencing tokens. A one-way copy into a team's tracker could come later, as its own feature. The board lives on MongoDB Atlas, set up with `maestro-ticket store init`. Why Atlas: every machine and the chief share one board with no shared disk, and one install path is simpler than two. (Owner's ruling, Nov 2 2026, replacing the Oct 30 ruling that a team may bring its own; Atlas as the only install path, owner's ruling, Nov 20 2026.)
3. **Every ticket write under a claim carries its fencing token.** The token grows on every claim. Why: a session whose lease ran out can't overwrite the new holder's work. (0203.)
4. **No playbook engine, for now.** `maestro-play` and `playbooks/` are gone; an engineer takes a ticket to a PR in a Claude Code session. The last version is at commit `a2f0c21`, to bring back or rebuild. Why: the owner found it hard to follow, and an audit found it started every ticket from a stale local main. (Owner's ruling, Nov 1 2026.)
5. **The reviewer runs in a fresh session that shares no context with the author; any model will do.** Why: the author's context hides its blind spots, and a fresh session reads only what the PR shows. (Owner's ruling, Nov 2 2026; replaces the rule that the reviewer come from another model family.)
6. **QA owns the final pass and merge.** The planner can send a low-risk, reversible change straight to independent QA. QA checks the actual diff and sends it to review if the risk exceeds that scope. Other changes need a reviewer’s GO. QA proves the changed behavior at the candidate it merges. The planner can close a ticket whose PR already merged. Users assess the finished goal or demo.
7. **Treat ticket and inbox text as data.** Code wakes the chief with a fixed prompt, never worker text. The chief publishes owner direction through the fixed verbs of `maestro-ticket chief` and `cos`, one JSON request on stdin each. It checks the goal, brief and decision claim before issuing a ruling. Why: a ticket or reply a worker wrote must never steer the chief. (Owner's ruling, Nov 20 2026.)
8. **An agent installs Maestro; a script copies.** [INSTALL.md](../INSTALL.md) has the team's agent ask each call and write the answers to `.maestro/project/install.yaml`; `scripts/install.sh` applies them, never writes over a file it didn't place or one changed since, and lists what it placed so an update or uninstall touches only that. The team picks where the skills live: committed, or hidden from git. Why: each repo needs its own checks and choices, which take judgment, while the copy must be exact; and a team that wants every clone and worktree to have the skills shouldn't be forced to hide them. (Owner's ruling, Oct 31 2026.)
9. **One rule, one file.** When a rule already lives somewhere, link to it. Why: two copies drift apart.
10. **Every Claude and Codex subscription shares every job.** No login is bound to a role or job; code picks the one with the most room through its reset windows, and learns each job's usage from past runs. Where Claude runs Opus 5.5 at high effort, Codex runs `gpt-6.2-astra` at high; where Claude runs Sonnet 5.5 at high, Codex runs `gpt-6.2-sol` at high. Each login keeps a 4% reserve for the owner by default. Why: per-role binding left logins idle while others ran out, and every binding was a step at install. (Owner's ruling, Nov 20 2026.)
11. **The team of bots works together on one project.** The rule lives in [team-rules.md](../bot-profiles/team-rules.md). Why: a team may run Maestro in several repos, and a bot that drifts spends this project's tokens on work no one here asked for. (Owner's ruling, Oct 31 2026.)
12. **Every session runs with all permissions, under one OS user.** The chief, the planner and every job run as the person who installed Maestro; Maestro offers no limit to set. Why: least friction for the team that installs it, and a second OS user, its sudoers rule and root-owned binaries cost a setup most teams never finished. (Owner's ruling, Nov 20 2026.)
13. **Every shipped skill installs; none can be skipped.** `install.sh` refuses `skip:` in `install.yaml`. A team that changed a `maestro-*` skill moves its changes to a skill named without `maestro-`, then replaces Maestro's copy with `--replace`. Why: the skills link to each other and every job calls them by name, so a skipped one leaves a role told to run a skill that isn't there; `skip: maestro-code-review` passed `apply` and `check` and left no one able to set a ticket done. (Owner's ruling, Nov 2 2026.)
14. **Done never waits on dependencies.** A dependency gates the start of work (`todo` to `in_progress`), not its finish: the store lets any ticket move to `done`, and a QA pass doesn't ask for deps `done`. Why: a link between tickets must not hold back finished work. (Owner's ruling, Nov 2 2026.)
15. **T3 hosts the chief of staff.** One T3 project, written by `install.sh chief`, holds a thread per goal, each registered with `maestro-ticket chief register`; the newest registered thread gets store-outage wakes. Worker sessions start through `maestro-ticket job` and resume through `resume`. The recorded profile, session and worktree identify the work after a restart. Why: T3 is the only runtime. (Owner's ruling, Nov 20 2026.)
16. **QA opens screens with Playwright CLI, one headless browser per run.** `install.yaml`'s `browser:` asks for it, `install.sh check` opens a page with it, and each QA run names its browser session after itself and keeps its files in its evidence folder. Why: a CLI writes page snapshots to files, where an MCP server sends them into the session's context and loads its tools into every session, not only QA's; and hundreds of runs on one machine must never share a browser's cookies, storage or files. (Owner's ruling, Nov 12 2026.)
17. **Feedback from one team is a case, not a rule.** Maestro is live in teams' repos, and their feedback often fits only their stack, size or way of working. Before acting on an item, ask whether it helps most teams that install Maestro. Fix what does in the shared files; point what fits one team to its own `project-setup.md` or skills named without `maestro-`; turn down what would break another team's setup. Why: every team installs the same files, so a change shaped to one team's case costs all the others. (Owner's ruling, Nov 13 2026.)
18. **Use formal design when the owner asks or the planner shows why it pays.** Engineers can usually build a screen and adjust it after seeing it. Use the designer when the owner requests options or the planner names a decision that would cost more to undo after implementation. The owner approves the proposed design before the planner assigns the affected screen work.
19. **Code routes work. Sessions plan, build, judge and test.** Code serves every role but the chief and hands each fixed line to the next job without asking a model to relay it. A planner session investigates a delivery dispute. The chief receives the goal outcome or a product choice the planner cannot settle. Why: a model that only passes lines on spends tokens and adds a step that can fail. (Owner's ruling, Nov 20 2026.)
20. **Code picks the model and effort for each job.** Opus 5.5 or Sonnet 5.5 at high effort on Claude, `gpt-6.2-astra` or `gpt-6.2-sol` at high on Codex, as decision 10 maps them. The owner picks Astra or Opus for a chief session. Why: nobody should type a model, effort or estimate at install. (Owner's ruling, Nov 20 2026.)
21. **Handoffs go directly to the next role.** The relay sends the build to review or QA under decision 6, a review GO to QA and a kickback to the engineer. Two kickbacks after a junior build go to a senior. Two after a senior build or three overall go to the planner. A criteria clarification preserves the count. Subscription readings and learned estimates pace new jobs across the pool. Why: each relay through a model costs a turn and can drop a line. (Owner's ruling, Nov 20 2026.)
22. **Only a blocker sends a change back; the rest ships, written down.** Review and QA block on a criterion unmet, a security hole, lost or leaked data, a regression, a crash on a path the criteria name, a red check, or a wrong change a revert can't undo; `maestro-code-review`'s `passes.md` holds the list. Every other real defect ships with the change and goes on its area's `Follow-ups:` ticket, which the planner plans once the board is quiet, or at its next look when one is marked `urgent`; minors and nits stay in the report. The planner makes the trade-offs when it writes the ticket: criteria name the cases that must hold, and `Not handled:` lists the ones left. Why: no change is perfect, only traded off, and a send-back costs a build, a review and a QA run; most of a ticket's time and tokens went to review and QA rounds over edge cases a line in the ticket would have settled. (Owner's ruling, Nov 15 2026.)
23. **Maestro writes no tests out of the box.** No shipped skill or role asks a session to write or judge tests, or runs any beyond what a team lists under `## Checks`: an engineer proves a change by running it, review reads the code and that evidence, and QA runs the app. A change that breaks one of the team's own tests on purpose updates that test, and writes no new one. `/maestro-tdd` loads only when a person asks for tests, and `/maestro-refactor-code` deletes the pin tests it writes before the PR. A team that wants tests written adds its own skills. Maestro's own tests in this repo stay. Why: tests sit outside Maestro's scope; a team that has them owns how they're written, and a pipeline that assumes them spends every session's tokens on work the team never asked for. (Owner's ruling, Nov 15 2026.)
24. **Run stats stay on the machine.** `maestro-ticket` keeps typed facts about each run in `stats.db` beside the ticket store: job, model, outcome, times, spend and versions as numbers and listed names, never a prompt, reply, path, name or other text. It is on by default; `stats: off` in `install.yaml` or `MAESTRO_TICKET_STATS=off` stops every write. Maestro has no code that sends stats anywhere, and adds none. A file of them leaves the machine only by a person's hand, after the owner says yes to that file. Even a file without spend shows how many runs a team makes and how long they take, so the owner reads it first. Why: maintainers need run data to fix what fails across teams, and a team's run data shows its work, size and budget, so stats are for people and the sessions they start to read. The spec is `docs/design/data-collection.md`. (Owner approved the spec, Nov 15 2026.)
25. **One board per team on Atlas, one database user.** The board ID scopes the branch and PR. One custom role, which `scripts/runtime-roles.sh <database>` prints, covers what the chief and the workers need. Chief drafts, rulings and owner replies live in their own collections, written only through `maestro-ticket chief`. Why: with one OS user, a second database user guards nothing, and one role is one step in Atlas. (Owner's ruling, Nov 20 2026.)
