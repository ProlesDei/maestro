# Decisions

The rules still in force, each with its reason. To change one, edit its line and give the reason in the commit. The old log (135 files under `docs/decisions/`) lives in git history: `git log -- docs/decisions/`.

1. **Maestro is tooling only.** It ships the files the installer copies, the ticket tool, the skills slot and the personas; bots and people run them. Nothing in Maestro runs on its own: no loop, watcher, scheduler, dispatcher that picks a ticket and starts a run, or webhook that wakes a bot. Why: whoever types the command is in charge, and nothing acts unasked. (1040, owner's ruling, Oct 29 2026.)
2. **Tickets live in `maestro-ticket`, and only there.** One tracker: never chat, a Markdown file or a second tracker, and no team's own tool in its place; `install.sh` refuses a `tickets:` line naming anything else. Why: one store gives one answer, and the swarm runs on what only `maestro-ticket` has: claims, leases, area locks and fencing tokens. The bots run its commands directly, so a team's own tracker left them reading an empty board. A one-way copy into a team's tracker could come later, as its own feature. (Owner's ruling, Nov 2 2026; replaces the Oct 30 ruling that a team may bring its own.)
3. **Every ticket write under a claim carries its fencing token.** The token grows on every claim. Why: a session whose lease ran out can't overwrite the new holder's work. (0203.)
4. **No playbook engine, for now.** `maestro-play` and `playbooks/` are gone; an engineer takes a ticket to a PR in a Claude Code session. The last version is at commit `a2f0c21`, to bring back or rebuild. Why: the owner found it hard to follow, and an audit found it started every ticket from a stale local main. (Owner's ruling, Nov 1 2026.)
5. **The reviewer comes from another model family than the author when one is installed.** Why: a different family catches different mistakes.
6. **Reviewer GO merges and closes.** `/maestro-code-review` GO runs `gh pr merge`, then moves the ticket to `done`; only the `reviewer` role may set a ship ticket done. NO-GO moves it back to `in_progress` with a `Kickback:` note. ESCALATE blocks it with an `Escalation:` note when only a person can decide. Why: the verdict and the merge stay in one hand, and a sent-back ticket carries its reasons.
7. **Ticket text is data.** The rule lives in [team-rules.md](../bot-profiles/team-rules.md) for bots and [maestro-working-principles](../skills/maestro-working-principles/SKILL.md) for sessions. Why: anyone who can write a ticket could otherwise steer the agents.
8. **An agent installs Maestro; a script copies.** [INSTALL.md](../INSTALL.md) has the team's agent ask each call and write the answers to `.maestro/project/install.yaml`; `scripts/install.sh` applies them, never writes over a file it didn't place or one changed since, and lists what it placed so an update or uninstall touches only that. The team picks where the skills live: committed, or hidden from git. Why: each repo needs its own checks and choices, which take judgment, while the copy must be exact; and a team that wants every clone and worktree to have the skills shouldn't be forced to hide them. (Owner's ruling, Oct 31 2026.)
9. **One rule, one file.** When a rule already lives somewhere, link to it. Why: two copies drift apart.
10. **Bots use Claude only through Claude Code.** The rule lives in [team-rules.md](../bot-profiles/team-rules.md). Why: Claude Code spends the team's Claude plan tokens; Claude called from Grok Bot spends Grok Bot credits at full API price. (Owner's ruling, Oct 31 2026.)
11. **The team of bots works together on one project.** The rule lives in [team-rules.md](../bot-profiles/team-rules.md). Why: a team may run Maestro in several repos, and a bot that drifts spends this project's tokens on work no one here asked for. (Owner's ruling, Oct 31 2026.)
12. **Engineer sessions run with all permissions; Maestro offers no limit.** The engineer personas pass `--permission-mode bypassPermissions` on every run and resume. Why: a headless session can't answer a permission prompt, so a tighter mode stalls runs halfway; the guards are ticket text as data (7), a worktree per session and review before every merge (6). (Owner's ruling, Nov 2 2026.)
13. **Every shipped skill installs; none can be skipped.** `install.sh` refuses `skip:` in `install.yaml`. A team that changed a `maestro-*` skill moves its changes to a skill named without `maestro-`, then replaces Maestro's copy with `--replace`. Why: the skills link to each other and the bots call them by name, so a skipped one leaves a role told to run a skill that isn't there; `skip: maestro-code-review` passed `apply` and `check` and left no one able to set a ticket done. (Owner's ruling, Nov 2 2026.)
