# maestro-ticket

The maestro ticket store and its CLI. People and bots call it to create, claim, move and comment on tickets. `Backlog.md` is a generated view of it.

Go, single static binary, no cgo (pure-Go SQLite and MongoDB drivers).

## Build, test, install

From `tools/maestro-ticket/`:

```sh
go build -o bin/maestro-ticket ./cmd/maestro-ticket   # build
go test -race ./...                                   # unit tests, race detector on
gofmt -l . && go vet ./...                            # lint
go install ./cmd/maestro-ticket                       # put maestro-ticket on $GOBIN
```

Tests are unit tests only, as AGENTS.md says. `unitonly/` lints them, and `cli`'s `TestMain` fails the package when a test starts the CLI, such as a launch's supervisor.

## Where the data lives

`--store PATH`, else `$MAESTRO_TICKET_STORE`, else `$(git rev-parse --git-common-dir)/maestro/tickets.db`. Every worktree of a repo shares the git common dir and git never commits it, so all sessions on all branches see one store and the working tree stays clean. A relative `--store` starts from the working directory; a relative `$MAESTRO_TICKET_STORE` is refused, since each worktree would read it as its own store. The git default needs git 2.31 or later, and refuses Maestro's own clone in `.maestro/src/`, which would make a second, empty store. It opens only a store that exists: a separate clone of the repo has its own git common dir, so every command there but `doctor` exits 2 `no ticket store` instead of making an empty one. `doctor`, which `install.sh apply` runs, makes the store.

**SQLite or MongoDB.** The store is SQLite unless a file named `store.uri` sits in the store's folder, beside `tickets.db`; then it is the MongoDB database that file's URI names, which machines with no shared disk can share. `store --uri-file F|-` writes that file (mode 0600, in a 0700 folder) from a file or stdin, so the URI stays out of shell history and off command lines, once the URI connects, and prints only the host; beside a SQLite board with tickets that never moved it refuses and names `migrate`, since this machine would turn to an empty board; `store --clear` removes it. A `store.uri` that can't be read, is empty or holds no `mongodb://` or `mongodb+srv://` URI is refused, never read as SQLite, which would make a second board. The URI's password never prints: errors and `doctor` name the host (`mongodb at <host>`). On MongoDB the folder still holds this machine's own state: `runs/`, `slots/`, `notify/`, `dep-cache/`, `checks/`, `backups/`, and `host-id`, a random id that names this machine on the shared board, since hostnames change. Supervisors and keepalives get the folder's path and read `store.uri` themselves. [Move between stores](#move-between-stores) says how a live board moves.

Before it opens the store, the CLI refuses (exit 2) a bare repo or a submodule when the path comes from git, a store directory on a network or VM/container-share filesystem (NFS, SMB, FUSE, 9p, virtiofs and others), and a directory where file locks don't exclude each other. `doctor` reports these as the `filesystem` and `locks` checks. `MAESTRO_TICKET_ALLOW_UNSAFE_FS=1` overrides both.

**Run stats.** Beside the store: `stats.db` (with `-wal` and `-shm`), typed facts about each run (job, model, effort, outcome, times, exit, turns, spend per model family, tool calls by step code from fixed lists, versions, disk free), never a prompt, reply, path, name or other text; `STATS_OFF`, which stops every write while it exists; and `stats.sha`, the Maestro commit `install.yaml` pins. `stats on|off [--maestro-sha S]` sets both, as `install.sh apply` does from the `stats:` key, at each apply and over a person's own `stats on|off`; with no key, apply runs `stats --maestro-sha S`, which records the sha and leaves the marker as it is; `MAESTRO_TICKET_STATS=off` turns stats off for one shell, and a store let onto an unsafe filesystem gets none. Only a run's supervisor creates or migrates `stats.db`, writing one row per run after its end (300 ms at most, or about 2.6 s for a run that ends while its start still waits on a busy `stats.db`) and pruning it after its first ring, once an hour across all supervisors: detail past 90 days or 256 MB rolls up into a daily table kept 400 days, and each session's last totals stay 30 days more, so a later resume counts only its own spend. `pickup` and `doctor` write the row of a run whose supervisor died only into a file already at their schema, wait 250 ms at most, and drop it otherwise. A stats error never prints. Nothing sends stats anywhere (decision 24); `rm stats.db*` wipes them and leaves tickets alone. [Run stats](#run-stats) lists the views.

`maestro-ticket render` writes `Backlog.md` next to the store, or to `--out`. It never lands in a work tree, so no branch can commit it. It writes a temp file, fsyncs and renames, with `<!-- generated by maestro-ticket render, do not edit -->` on line 1. The output depends only on the store and on which leases have run out, so re-rendering an unchanged store changes nothing but a claim that turned `(expired)`.

## Guarantees

- **One writer at a time.** SQLite in WAL mode, `busy_timeout=5000`, `synchronous=NORMAL`, `foreign_keys=ON`. Every write is one `BEGIN IMMEDIATE` transaction: the change and its event commit together or not at all. Readers never block writers.
- **Leases, not locks.** `claim` gives `<bot-id>/<session-id>` a lease for `--ttl` (default 30m, 5s to 24h). `heartbeat` renews the lease to `--ttl` from now (default 30m) and never cuts a longer one short. An expired lease is lost and the ticket is claimable again, so a crashed session frees its work without cleanup. Until someone writes to the ticket or reaps (as `alerts` does each look), though, the holder's heartbeat revives it and logs `lease_revived`: a machine that slept past the lease keeps its work, since every write frees an expired lease first and every claim takes a new token. The claim counts its revivals (`claim.revivals`; `list` shows `holder (revived 2x)`), since even one means its session slept, hung or lost its keepalive. It stays lost if another claim took one of its areas meanwhile. `release` is safe to repeat; `release --died` frees the lease of a run that hung or died and adds one to `lease_expiries`, as an expiry would. A claim does not change status.
- **Kill switch.** While a file named `STOP` sits next to the store (`<git common dir>/maestro/STOP` by default), every `claim` fails with exit 4 `stopped`, its message starting `refused:`, and no lease that ran out comes back. `list --ready` still lists. `stop --all` makes that file, and `stop --all --off` removes it if `stop --all` made it. On MongoDB, `stop --all` halts every machine, and `stop --all --off` lifts it. The halt commits as a write, so no claim already under way commits after it; each machine copies it to a local `STOP` file marked as its own, for the skills and bots that look for the file, and `--off` removes only files with that mark. A machine makes that copy when it runs `look`, `job`, `slot`, `heartbeat` or a keepalive's heartbeat, so a session already going sees the halt within one keepalive interval (10 minutes by default); one that holds no claim sees it only once something else on its machine makes the copy. A `claim` or `heartbeat` that finds the copy reads the board first, so a lifted halt clears it. A board a machine can't read is no halt there: `job` and `look` fail with the board's error. A `STOP` made by hand still stops its own machine.
- **Low disk.** `claim` refuses with exit 4 `low_disk`, its message starting `refused:`, while the store's, the temp dir's (`$TMPDIR`) or the working directory's filesystem has under 10% of its inodes free and under 1Mi of them, or under 10% of its space free and under 10 GiB, so no run starts work it would die halfway through, holding a claim it may not be able to release. The floors keep a big disk with room to spare working. `MAESTRO_TICKET_MIN_FREE` sets the percent (0 to 99; 0 turns the check off). `slot` checks the same once its slot frees. A store write that runs out of disk (SQLite's `database or disk is full`) fails with `low_disk` too. No other command checks the margin, so `release` works while the disk has any room left.
- **Heartbeats from a background process.** `claim --keepalive PID` starts a detached `keepalive` that heartbeats every TTL/3 while process PID (one of yours, not PID 1) lives. It stops when PID exits or turns zombie (the lease then expires) or when the lease is released, lost or re-claimed. `claim` and `keepalive` refuse with exit 2 their own PID, or a PID in their session when that session has no terminal: Claude Code, Codex and Grok Build run each command that way, so that PID (the shell, `$$`, or a wrapper such as `timeout`) exits with the command. Pass the shell's parent, the harness. From a terminal, `$$` is your login shell and is accepted. The check relies on that: a harness that gives each command a terminal (Codex can) lets a wrong `$$` through, and one that runs commands in its own session with no terminal gets even `$PPID` refused.
- **Expired leases are logged.** `reap` frees every expired lease, logs `lease_expired` (actor `maestro-ticket`, data `holder`, `token`, `expired_at`, `expiries`), adds one to the ticket's `lease_expiries` and checkpoints the WAL. Any write to a ticket with an expired lease does the same first, so no expiry goes unlogged. Freeing an expired lease doesn't change `version`.
- **Fencing tokens.** Every claim returns `claim.token`, a lease number that grows on every claim of the ticket, re-claims included, and is never reused. `heartbeat` and `release` always need `--holder` and `--token`; on a claimed ticket, so do `transition` and `comment`. Another holder gets exit 4 `claimed` (`lease_lost` for heartbeat), a missing token exit 2, a stale token exit 4 `lease_lost`. A write that names a lease it no longer holds gets `lease_lost` even if nobody holds the ticket now. On an unclaimed ticket, `transition` and `comment` need neither flag.
- **Optimistic versions.** `claim`, `release` and `transition` bump `version`; `heartbeat` and `comment` don't. `transition --from S --expect-version N` fails with exit 4 if someone else got there first. Moving to `done` or `cancelled` clears the lease.
- **Idempotent retries.** `--idempotency-key K` on `create`, `update`, `claim`, `release`, `transition`, `comment`, and on `verdict` and `handoff`, which require it: a retry with the same key and request returns the first result and writes nothing; the same key with a different request fails with exit 4. For `update`, `transition` and `comment` the lease token isn't part of the request, so a session that claimed again retries under its new token; a `release` names one lease, so its token is. Replaying a `claim` key returns the ticket as it is now while that lease is live, and fails with `lease_lost` once it is gone. Replaying a `create` key returns the ticket as it is now, and fails with exit 4 once it is cancelled. Failed writes don't use up the key.
- **Append-only events.** Every write appends to `events` (triggers reject update and delete). `seq` only grows, and events commit in seq order, so `events --since N` with the `next_seq` from the last call never misses or repeats one.
- **Backups.** `backup [--keep 24]` writes a checked `VACUUM INTO` snapshot to `backups/` next to the store (through `<name>.partial`, so a crash never leaves a part-written file under a snapshot's name) and prunes older snapshots (only files named like one, never the store) and any `.partial` an hour old. `export` prints the store as one JSON document. To restore, stop writers, `maestro-ticket keepalive` processes too, copy a snapshot over `tickets.db` and delete `tickets.db-wal` and `tickets.db-shm`. Then reset every `events` cursor to the restored store's last seq. Ticket ids made after the snapshot come out again, so a `maestro/<id>` branch or PR from then names another ticket now: rename or close it first. `backup` and `export` never copy `stats.db`.
- **Schema migrations.** `PRAGMA user_version` records the schema. Opening an older store first snapshots it to `backups/<store name>-pre-schema-v<n>.db`, such as `tickets-pre-schema-v1.db` (once; `backup --keep` never prunes it), then runs each missing step in order, in one transaction. A newer store is refused with exit 2 `store_too_new`: rebuild `maestro-ticket` from the newest Maestro on the machine.

## MongoDB store

The same `ticket.Store`, with the same guarantees as above where they don't name SQLite. What differs:

- **One writer at a time.** Each write is one transaction (snapshot reads, majority writes) whose first step updates the `meta` collection's writer document, so writers take turns as `BEGIN IMMEDIATE` makes them on SQLite. That document also holds the id and seq counters, so ids and `seq` stay dense. A write that keeps clashing retries for about 30 seconds, then fails with exit 4 `busy`; a commit whose result is unknown retries only the commit.
- **The server's clock.** Leases, events and every time a write stamps come from the database's clock, read in the same transaction, never a machine's own, so two machines whose clocks differ agree on when a lease runs out.
- **Only a move starts a board.** `migrate --to mongodb` makes the board in an empty database; every other command, `doctor` and `look` among them, refuses a database that holds none (`holds no board`) and writes nothing there, so a URI that names the wrong database can't split the team across two boards.
- **Append-only events.** The code never updates or deletes an event, and the setup in [INSTALL.md](../../INSTALL.md#move-the-board-to-mongodb) gives the database user no `update` or `remove` on `events`.
- **Shared coordination.** Handouts, job marks, the usage pause and the `stop --all` halt live in the database, so two machines never send or start the same job; runs, slots, rings and chains stay on the machine that started them, which finishes its own runs. Another machine's runs count as live until their limit plus the slot wait has passed, one a usage limit stopped holds its ticket until a `--stall` past the limit lifting, and `alerts` never marks one died or frees its claim before its limit plus 8 hours.
- **Doctor** checks that the server answers and transactions work, that `transactionLifetimeLimitSeconds` is 10 or less (a run killed mid-write otherwise holds every write for 60 seconds), the schema version, that counters are at or past the highest ids and `seq` has no gaps, times one write, warns while `stop --all` holds, and warns when this binary is older than one that wrote the board, or when machines last wrote with different builds.
- **Backups.** `backup [--keep 24]` writes the whole board, idempotency keys included, as one JSON file, `backups/tickets-<time>.json`, and prunes those as it prunes snapshots.

## Move between stores

Both moves refuse unless new work has stopped, and neither starts on its own: `install.sh apply` only tells a team to run one.

- **`migrate --to mongodb [--uri-file F|-]`** needs `STOP`, and no live runs or claims on this machine. It reaps, then, in one SQLite write transaction, copies every table as it is (idempotency keys, lease tokens and the id counters included, and this machine's `host-id` on each launch) into a MongoDB board that must be empty or hold the same copy (a file that moved already goes to no empty database, since a second copy would fork the board); checks the copy table by table, row by row (a hash of each), with matching counts, last `seq` and `export`; adds triggers that refuse every write to the SQLite file with `board moved to mongodb`, so a process that still has it open can't write a second board; and writes `store.uri`, from `--uri-file` or as it stands. The handouts and the pause go to the board with it, and a `STOP` that `stop --all` made becomes the board's halt. The file still reads, and `doctor` on it fails. `tickets.db` stays where it is, never renamed, as the way back: its last writes may still sit in its `-wal`.
- **`migrate --to sqlite`** needs `stop --all`, and no open runs or live claims on any machine. It copies the MongoDB board back into the SQLite file, empty or the one it came from, and drops its triggers, checks the copy the same way, brings the handouts and the pause back, marks the MongoDB board moved, so every call to it fails from any machine, removes `store.uri` and lifts the halt here.
- **Cut short.** While a move copies, the MongoDB board is marked moving, and every call to it but the move's own fails with `board moving`; only the machine that started the move can finish it. Run the same `migrate` again there: it picks up where the last one stopped. Or, for a move to SQLite, call it off there with `migrate --to sqlite --abort`: a copy it made in the SQLite file takes no writes again, the MongoDB board takes writes from every machine, and the halt stays until `stop --all --off`. If that machine is gone, `migrate --to sqlite --abort --force` calls the move off from any other; only once you know it is gone, since a move it still runs would copy a board that takes writes again (it can no longer mark the board moved, but its SQLite copy goes stale). A copy too big for one MongoDB transaction goes in outside one, so events, which the database user may only add to, are checked and added, never rewritten.

## Runs

Bots start every Claude Code session with `launch`, so none waits on a run and none goes unread.

- **`launch [--ticket T-1] [--limit 2h] [--rings 0s,5m,10m,40m] -- claude -p <flags>`** reads the prompt from stdin, records the run in `runs/` next to the store (launcher from `--actor` or `$MAESTRO_TICKET_ACTOR`, ticket, limit, command, folder, machine, start time) and hands it to a detached `supervise` process, then prints the run id (`R-` and 8 letters) and exits once the command runs. A command that can't start fails `launch` with exit 2, and nothing else reports it. `--limit` (1s to 24h) is the time limit, which leaves out the time the command waits for a `slot`, up to 8 hours (a long QA line); a command that starts `timeout <duration>`, as an older rule wrote it, gives the limit that way instead. `NAME=value` words before the command set its environment, as in a shell. A stdin that stays open and sends nothing for 3 seconds counts as empty; once text comes, it reads to the end. The command runs in the launcher's folder with `MAESTRO_RUN_ID` and `MAESTRO_TICKET_ACTOR` set, in a process group of its own.
- **The supervisor** waits for the command. The limit runs on the wall clock from the run's start, as leases and rings do: every 2 seconds the supervisor reads the clock and looks for a stop someone asked, since a timer on the monotonic clock stops while a host freezes the VM. A run frozen past its limit ends within seconds of waking, and its error says how long the machine was frozen; a timeout the freeze caused (the run had time left by the monotonic clock, and the freeze took half its time or more) is marked `frozen`, and pickup counts it as no repeat timeout or stopped build and runs such a review or QA again at its limit, so one freeze escalates nothing. At the limit it sends the group SIGTERM, then SIGKILL 10 seconds later to whatever of the group is left, and records `timed_out`. What left the group goes the same way (on Linux, every process with the run's `MAESTRO_RUN_ID`): a tool command Claude Code started in a session of its own, or a `slot`'s command, so a hung test or server holds no port or slot past the limit. A run that `launch` started from inside another run is its own, and stays. Otherwise it records `done` (exit 0) or `failed` (any other exit; 128 plus the signal for one a signal ended), with the exit code, the reply and session id from Claude's `--output-format json` (or the output's last 4 KB), and stderr's tail on a failure; the whole output stays in `runs/<id>.out` and `.err`. With stats on, on Linux, and with room on the store's disk as `claim` asks, a run that `job`, `job again` or `resume` started runs with `--output-format stream-json --verbose` in place of its command's `--output-format json`; its record keeps json. Its stdout goes to `runs/<id>.stream` (mode 0600), which the supervisor reads once the command ends, for stats.db's tool counts, and removes once the run's end is recorded (`pickup` or `doctor` read one a dead supervisor left into an empty `.out`, as it would have, then remove it). `.out` then holds what json would have printed: the command's own text, then the last result line, unless the session went on past it or the run was killed. Then it logs the run's cost, as `log-run` does, and for a run with no result (`timed_out`, or `failed` with no session id) frees its ticket's live claim with `--died`, if the holder is the launcher's and no other live run is on that ticket. It holds a lock on `runs/<id>.lock` while it lives, so a run whose supervisor was killed, or whose machine restarted, reads as `died`; on Linux the kernel then sends the command SIGTERM, though not what the command started. Unix only.
- **Chain.** Before the first ring, while the record is `settling` (no reader lists it as a result), every `job` run's end is routed as `pickup` would route it and the route is stored (`routed`), so the ring and every `pickup` show the same lines. A supervisor a shutdown stopped leaves the end `settling` and starts nothing, since what it started would die with the machine; the first reader after routes and chains it. A `build`, `review`, `qa` or `live` run that ended done then starts each `send` that is a fixed job for a worker bot (`build <id>` to an engineer, `review <id>` to the reviewer, `qa <id>` to the QA lead) starts as `job` would, as that bot, so no bot spends a turn passing it on. The new run gets the ending run's environment, folder and machine, with `MAESTRO_TICKET_ACTOR` set to the bot it is for, and QA runs take `rules set qa_slots`'s count, else the `--slots` the QA lead's newest QA run passed, so a new slot count reaches chained runs once the QA lead starts one by hand. The chain gives up after 2 minutes, so a hung `gh` holds no ring. The new run's record names the run that started it (`chain_of`) and its `hops`; a run 10 hops down starts nothing. It starts none for a bot with no webhook, for a send a look made lately, or when `job` refuses (`stopped`, `paused`, `claimed`): that send stays for the launcher's `pickup`, as before. What it started goes in `chained`, and `pickup` shows the stored route rather than routing again, since the ticket has moved on. When the launcher has a webhook, what is left only for the planner, with no `do:` line, reply or failed write, goes to the planner if it has one too (`notify`): its webhook rings, its `pickup` shows the run and it acks it; and a run that leaves nothing to do is acked by `chain` and rings no one. A launcher with no webhook, such as a person, keeps the run in its `pickup`, though the bots' next step still starts. A stored route's follow-ups that failed to file are filed again at each `pickup`. For a `build`, `review`, `qa` or `live` run, however it ended, the end first runs each `do:` line of a fixed shape itself, as the launcher, when the launcher has a webhook: `resume <run> --died`, `resume <run> --go-on` or `job again <run> [--limit D]`, for that run only and never another command. What it ran goes in `chained`, and the command acks the run; one that refuses (`paused`, `stopped`, another start of it under way) stays for the launcher's `pickup`. A run that ended short starts no `send`, and one whose route gave it nothing to do is never acked by `chain`.
- **Rings.** Once the run's end is settled, the supervisor POSTs a digest as JSON to the owner's webhook (the launcher, or the planner a chain left the run to) at each `--rings` time after the end, until the owner acks the result: `text`, `bot` and `launcher` (the owner), `run`, `ticket` and `state` of its newest result, `lines`, `ack` (the command that acks the runs whose lines ride), `runs` and `more`. The digest covers every settled result left to the bot that it hasn't acked, 10 runs at most and under 4 KB, in `pickup`'s order and with its rules (a send a look made lately left out, the runs a usage limit holds as one line, a run with a `do:` line left out of `ack`). A run's lines ride only when each has a fixed shape (a job for a worker bot, a fixed planner line, a fixed `do:` or `wrote:`); a run with any other line, a reply, any line to the chief of staff but a fixed fault line, or no stored route rides whole in `pickup`, counted in `more`, behind one `card waiting: run pickup` line. Each bot has a gate (`notify/<bot>.gate`, under `notify/<bot>.gate.lock`): while a ring under 4 minutes old listed a run still unacked, no supervisor rings that bot; one whose run that ring listed counts it as rung, and one whose run it didn't waits for the gate to open and rings then. A ring that failed holds the gate too, and covers nothing. A webhook with a key gets it as `Authorization: Bearer`. With no webhook, it rings nothing. `notify --test` skips the gate.
- **After a restart.** A supervisor that went away before a ring got through (the machine restarted, it was killed, or a shutdown stopped it) leaves a run no one would ring for. The first `pickup` or `doctor` after it, whoever runs it, takes the run's lock in the supervisor's place, so one reader at a time and no late supervisor can write it. A run with no result it saves as `died`, kills what is left of it (on Linux, every process with its `MAESTRO_RUN_ID`), and frees its ticket as above; then it routes it, and any run whose supervisor died mid-way through its end, as that run's launcher, and rings: one ring per bot through its gate. A run the gate held back, or that a ring only counted in `more`, stays for a later look; a ring that fails is tried again on later looks, up to 5 times. A `pickup` rings no one for its own bot's orphans: it shows them, and marks those it shows rung. A record that names another host is this machine's under an old name (a Mac's changes with its network, a container's on a restart), and reads by its lock like any other. Only with `MAESTRO_TICKET_ALLOW_UNSAFE_FS=1`, where the store may sit on a disk machines share, is such a run left alone, its lock out of reach, until no supervisor would still run it: its limit, 8 hours of slot wait and an hour past its start.
- **`job <job> [<id>...]`** starts a bot's job as a run, as `launch` does, with the prompt, model, effort (high), time limit, session id (`--session-id`, a fresh UUID) and lean start (`CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`; runs that run no checks add `CLAUDE_CODE_PROMPT_CACHE_TTL=5m`) set for it, so a bot spends one step and names no flag. `build <id>` runs `/maestro-software-engineer` on Opus, or Sonnet for a `junior` ticket until it has been sent back twice, when it goes to the senior engineer. `review <id>` runs the review skill's `review-prep.sh --route` first (from the checkout, else the main one, where skills hidden from git live): a docs-only PR reviews on Sonnet with `--light`, any other on Opus (`--full` forces it; with no `gh`, it reviews full), with a limit of 45 minutes plus 15 per 200 changed lines, at most 2 hours; `--approved <sha>` and `--drop <ids> --drop-file F|-` pass a ruling on. `qa <id>`, `live <id>` and `qa-ask` (the ask on stdin) run `/maestro-qa-lead` on Opus, each through `slot --name qa`, so at most `--slots` (else `rules set qa_slots`'s count, else 6) run at once and the rest wait in line. `plan`, `judge <id>...` and `cos` (text on stdin; a `plan` or `rule` prompt gets `rules.md`'s lines after it, as `Standing rules:`) run `/maestro-planner` or `/maestro-chief-of-staff` on Opus; `rule <id>` (the decision on stdin) on Opus too, since a ruling may split, rewrite or plan a design's screens, and `finish <id>` on Sonnet. `design <id>` runs `/maestro-designer` on Opus. A `build`, `review`, `qa`, `live` or `design` session gets a Stop hook through `--settings`: `<this binary> stop-check --store <the store>`, the store named only there, never in the session's environment, so a `maestro-ticket` the session runs in another repo finds that repo's store. `stop-check` blocks the session's end, telling it to wait for its subagents and background work and post its note or reply `<job>: refused: <why>`, unless it ended one of the ways its route reads: the job's note (`Handoff:` or `Escalation:` for a build; `Review:`, `Kickback:` or `Escalation:` for a review; `QA:`, `Kickback: QA fail`, `Rereview:` or `Escalation:` for QA; `Live run:`, `Hold:` or `Escalation:` for a live run; `Design spec:`, `Escalation:` or `Sent up:` for a design) posted since the session's first run began, the ticket out of the job's statuses or held by another bot, a refusal, a Sonnet build's question, a review's `stopped: tier` or report-only, or a QA or live `refused` or `blocked`. It blocks a run twice at most, and lets the end through on any error, a session or run it doesn't know, `stop_hook_active`, a stop asked, `STOP`, a pause, under 3 minutes left, or a usage limit; a run it let through past its blocks (`runs/<id>.stopcheck` says `capped`) counts as a review or QA run with no verdict even if it then timed out, and the block that follows names how many. `job again` and `resume` give the new run one fresh hook on this binary as it is now. `--model`, `--effort` and `--limit` override; `--ticket` names a text job's ticket. It refuses (exit 4) a ticket in a status the job can't work (a build in review, a review not in review, a review whose `Review: GO` stands), a second run of one job on one ticket while the first goes (`claimed`; a `<ticket>.<job>.active` file in `runs/`, made with `O_EXCL` before the run starts, given the run's id before its command runs (a start that can't write it fails), and removed when it ends, so of starts at once only one runs; a live run on the ticket from before `job`, or from plain `launch`, holds it too), any job while `STOP` sits next to the store (`stopped`), and any job while a usage limit `pickup` saw holds (`paused`, with the time it lifts). A start another session of the same bot already made prints `<run> already going: nothing to do` and exits 0. `job again <run-id> [--limit D] [--full]` starts that run's job afresh: its prompt and command as they were (`--approved`, `--drop`, `--slots` kept), a new session, and a new limit, or with `--full` a light review on the full model. A planner job run again holds its ticket from `look`'s starts, as `look`'s own start would. A run goes again once, whoever asks: `runs/<run>.again`, made with `O_EXCL` before the start and taken back if the start fails, names the run it started, and a later `job again` of it prints `went again as <run> already: nothing to do`. The new run names the run it retries (`again_of`) and keeps its `chain_of` and `hops`, as a resume does. It prints one line for the run, then, when any of the actor's runs ended and isn't acked, `<n> ended, unacked: run pickup`.
- **`resume <run-id>`** resumes that run's session as a new run with the same command, ticket, limit and job, the answer on stdin, and acks the old run. `--opus` moves it to Opus at high effort, as for a junior build's stuck session (with no answer, it tells the session to settle its question or send it up). `--go-on` resumes a session a usage limit stopped. `--escalate` tells a build that ended on a question to post it as an `Escalation:`; `--decide` tells a planner session to make its own calls and send the chief of staff's up as `up:` lines. `--opus`, `--escalate` and `--decide` each come once per session (the run records it as `nudge`): a session that asks again goes up instead. `--died` resumes a run that died with `Your run died. Go on from your last step.`, once per session; a run its supervisor stopped when the machine shut down (`the launcher was stopped`) routes on its ticket as any failed run, but where its work hadn't landed pickup offers it `--died` in place of a mismatch, and it counts as no stopped build or review with no verdict. It refuses a ticket that moved on without the session (a build's in review or closed, a review's or QA's out of review: ack the run instead), a run resumed already, even by a resume beside it (a `<run>.resumed` file, made with `O_EXCL`), and refuses under `STOP` or a pause as `job` does. A judge run resumes with its tickets, so `look` counts them busy, and every run with its `chain_of` and `hops`. A slot-wrapped run resumes through this binary, wherever it now lives. Only the run's launcher resumes it.
- **`pickup`** prints each run left to the actor (one it launched, or one a chain left to the planner) that has ended and that it hasn't acked, every time, and lists the actor's runs still going, a run whose end is still settling as `ending`. A run `job` or `resume` started is sorted, not printed whole: one line `<run> <job> <outcome> on <ticket> (<status>): <the reply's first line, or the exit code>`, where the outcome is `done`, `question`, `usage_limit` (with the reset time the reply gave), `disk_full`, `timed_out`, `died`, `refused` or `failed`; then `send <bot>: <line>` for each message the bot sends, `do: <command>` for a command it runs, `wrote:` for each write pickup made, and `mismatch:` when the ticket isn't where the job should have left it. The routes: a build in review goes to the reviewer (and the planner hears `slot free` only while a ready `todo` waits); a junior build's question (a Sonnet run that asked, or blocked on an `Escalation:` that isn't an `outside step:`) becomes `do: maestro-ticket resume <run> --opus`; an Opus build that asked without posting becomes `resume --escalate`, and one that asks again after it has the question posted for it as `Escalation: build: <question>` and its ticket blocked (a note pickup writes carries `Posted-by: pickup <run>`, so a second pickup of the run routes as the first did; pickup writes under no other bot's lease); an escalated build goes to the planner, and pickup releases the claim its stopped session left, so the judge needn't wait out the lease; a build that ran out of time or failed (not a refusal, a stop asked, a stopped launcher or a start that never ran) on a `todo` or `in_progress` ticket no other bot holds becomes `do: maestro-ticket job again <run>`, with twice the limit (at most 4 hours) after a timeout, once per head (its latest `Handoff:`, `Kickback:` or `Answer:`), and pickup releases the claim the stopped session left, counting no lease expiry (`wrote: released <id> for the retry`); one a freeze ended goes again at its own limit, twice at most per head; a second timeout or failure at one head, or a freeze past those two, blocks the ticket with `Escalation: build timed out or failed twice with no handoff` for the judge; one on a ticket that moved on or another bot holds sends the planner `timed_out <id>`; a GO goes to the QA lead as `qa <id>`; a review or QA send-back goes to the engineer who last claimed the ticket at TRIES 0 or 1, a junior's ticket to the senior at 2, and the planner otherwise; a `Rereview:` goes to the reviewer; a QA pass sends the planner `merged <id>` while work remains (a ready `todo`, or its goal still open), since a merge frees what waited on it, or `goal <slug> done` when it finished its goal; a failed live run sends `live fail <id>`, and `look` plans its fixes; a ready design's card goes to the chief of staff as its session wrote it, and the ticket is marked `Sent up:`; a light review that needs the full model becomes `do: maestro-ticket job again <run> --full`; a first death becomes `do: maestro-ticket resume <run> --died`; a run that timed out, hit a usage limit or died after its work landed (a build's `Handoff:` or `Escalation:`, a review's verdict, QA's merge, send-back or `Rereview:`) routes on its ticket as one that ended done would, so its next step is never lost, and sets no pause, which would refuse that step; a block, full disk (with the reply's first line), refusal or second death goes to the planner. A usage limit (Claude Code's own words opening the reply) pauses every job (`paused.json` next to the store) until the reset the reply names, or an hour after the run ended, and tells the planner once per pause, frees the claim a stopped build left (no lease expiry), and prints `do: maestro-ticket resume <run> --go-on` (the session goes on where it stopped, with the answers it was given; `job again <run>` for a run with no session), which refuses until the pause lifts; the run stays unacked, its supervisor rings its bot once when it ends and once more as the limit lifts (none between), while the pause holds pickup shows such runs as one `<n> runs wait` line with nothing to retry or ack, a Claude session waiting in a `slot` line holds till it lifts (and under `STOP`), and `look` keeps its ticket for it until a `--stall` past the lift (so a ring a reboot lost holds nothing for good); the run that set the pause shows whole, so its bot tells the planner; a reset already past pauses nothing. A review or QA run that ran out of time goes again with twice the limit (at most 4 hours; one marked `frozen` goes again at its own limit, twice at most per head, and counts as no timeout until then), as `do: maestro-ticket job again <run> --limit <d>`; a second timeout at one head (since the latest `Handoff:`, or the move into review when there is none, or `Review: GO` for QA) blocks the ticket with `Escalation: review at <sha>: ran past <limit>` or `Escalation: QA at <sha>: ran past <limit> twice`, and `Return-role:`, keyed by the run so a second pickup writes nothing. After a review or QA run (not a live run, whose findings become its fixes), what it let ship or found outside its ticket (a review reply's `## Follow-ups` lines, the `New tickets:` line of a QA verdict posted during the run, and the reply's `Open:` line) goes on the `Follow-ups: <area>` ticket of the ticket's first area as one comment; that ticket, made in `backlog`, parked `deferred`, with no goal, comes once a day at most per area, whichever bots pick up at once. `look` sends an item marked `urgent` to the judge. A follow-up that can't be filed (its ticket held) prints `wrote: follow-ups not filed` and the run routes on. The reply prints only for a `cos` or `qa-ask` job, whose reply is the answer; a `judge`, `plan`, `rule` or `finish` reply turns into its `send` lines, an `up:` line going to the chief of staff (for a planning run, as `<job> <run>: <card>`, so the answer can resume it), and a planning run that stopped on a question with no card becomes `resume --decide`; asked again after that, its question goes to the chief of staff as a card. A judge run that gave no answer frees its rows for the next look, unless it died once (its resume works them); a planning run that failed or timed out with no card goes again once as `do: maestro-ticket job again <run>` (pickup releases the claim its session left, and its ticket stays held); a second such end (the run is a `job again`, or resumes one), a refusal, or a ticket another bot holds sends the chief of staff one fault line, `failed twice <job> <run>[ <id>| goal <slug>]`, `refused <job> <run>[ <id>]` or `failed <job> <run> <id>`, marks its ticket `Sent up:` and frees it for no look's start; one whose ticket closed or went to review needs neither (`wrote: <id> moved on`). Any other end short of done that its route gives no line, command or reply, its ticket still open, sends the chief of staff `<job> <outcome> <run>[ <id>]: nothing routed`; a failed `cos` or `qa-ask` shows its error as the reply. `--full` prints every reply; `--json` adds `routes`. It shows 20 ended runs at most, those it can act on first, then `and <n> more ended`; a send a look made in the last 20 minutes it leaves out, and it marks its own, so a second pickup of the run shows them again and the next look sends none; one made before the run began was for the step before it (the review a quick send-back answered), so the run's own takes its place. The last line names every run to ack in one `ack` command, but a run with a `do:` line, which that command acks when it starts. The first review or QA run in review that ends with no verdict since its `Handoff:` (or `Review: GO`), not stopped on purpose, becomes `do: maestro-ticket job again <run>`; the second sends the planner `mismatch <id>`. A review or QA run that ended with no verdict for the third time since its `Handoff:` (or `Review: GO`) blocks its ticket for the judge the same way. A planning run that sends a card up for a ticket marks it `Sent up:`, and `look` leaves any ticket under a latest `Sent up:` alone, whatever its status. A build that stopped with no handoff for the third time since its last handoff, send-back or answer, however it stopped, (a crash before its session claimed the ticket included) blocks its ticket with an `Escalation:` for the judge. It removes the files of runs acked over 7 days ago; a result no one acked stays until someone does. A record it can't read, such as one a crash cut short, lists as `unreadable` rather than vanishing. The reply and error are set four spaces in, as `get` sets a body.
- **`ack <run-id>...`** records that the actor acted on each result: `pickup` stops showing it and its rings stop. Only the run's owner acks it: the bot that launched it, or the planner a chain left it to (exit 2 for another). A launcher whose pickup listed a run before its end left it to the planner gets `<run> is left to planner: nothing to do`, and the rest of its batch is acked. It makes `runs/<id>.acked` exclusively, so however many sessions ack at once, one ack counts; a later one prints who acked it. A run still going can't be acked (exit 4). Its last line, `<n> more unacked for you: run pickup` (and `more` in `--json`), counts the actor's settled results still to ack, those a pause holds aside.
- **`stop <run-id>`** ends a live run as its limit would, on the same kill path, and records it `failed` with `stopped by <actor>`; its supervisor rings the launcher, so `pickup`, `job again` and `resume` work on it as on any end. It writes `runs/<id>.stop` with `O_EXCL`, which the supervisor looks for every 2 seconds, and waits up to 20 seconds for the end (exit 4 if the run still goes). Only the run's launcher or the planner stops it (exit 2 for another); an ended or died run refuses (exit 4). `job again` and `resume` refuse a live run with a pointer to `stop`.
- **`runs [<run-id>] [--all] [--launcher B]`** lists runs not yet acked (`--all` adds the rest) without acking any; with an id it prints that run in full. On Linux it also lists `untracked`: each `claude -p` (or `--print`) process working in a worktree of this repo whose environment has no `MAESTRO_RUN_ID`, so launch didn't start it. It skips its own ancestors. `doctor` adds a `runs` check that warns, without failing, while one of those runs, or while a run's result has waited over 15 minutes for its launcher's ack (a died one at once).
- **`notify [<bot-id>] [--url-file F|-] [--key-file F|-] [--clear] [--test]`** keeps one webhook URL per bot in `notify/<bot-id>.url`, and the bearer key it wants in `notify/<bot-id>.key`, next to the store, mode 0600, outside every work tree. `-` reads one from stdin, so it stays out of shell history; `--clear` removes both; `--test` rings once. It never prints the URL, only its host, nor the key; with no bot, it lists the bots that have a webhook.

## Roles and workflow

Roles: `chief-of-staff`, `planner`, `engineer`, `qa-lead`, `reviewer`, `designer`. Review comes first and QA last, both in `in_review`: the reviewer records a pass as a comment starting `Review: GO`, and the QA lead a pass as one starting `QA: pass`; there is no QA status. `create --role`, `claim --role`, `transition --role` and `--actor-role` refuse any other name (exit 2).

Statuses and moves live in `ticket/ticket.go` (`workflows`), one table per ticket type (`create --type`, default `ship`):

- **ship:** `backlog → todo → in_progress → in_review → done`. Only `--actor-role qa-lead` (or `$MAESTRO_TICKET_ROLE=qa-lead`) sets done, once QA passed and merged the PR, or `--actor-role planner` when the PR merged outside QA.
- **scout:** `backlog → todo → in_progress → in_review → done`. Only the ticket's owner (`create --owner`, default the creator) sets done, as `--actor`.

Both allow `in_review → in_progress` (send-back), `in_progress → todo` (escalation) and `todo → backlog`. Any non-terminal status can go to `blocked` or `cancelled`; `blocked` goes back only to the status it came from (`blocked_from`), except that a scout ticket with role `designer` and a title starting `Design:` may also go straight to `done`, by its owner: the owner's yes on a design closes it in one move. `claim --next` never hands out `backlog`; claim those by id. A send-back adds one to a ship ticket's `tries`; a scout send-back doesn't. `create --split-from <id>` starts the new ticket at that ticket's `tries`, so a split or rewrite keeps the count. A ticket re-filed by hand without it can be linked later: `update <new> --split-from <old>` adds the old ticket's `tries` to its own, once, and takes its goal when the new ticket has none and the call sets none. The old ticket must be `cancelled` with no ticket split from it yet, and the new one not split from another; a link that would loop is refused, and a retry of one that went through changes nothing.

The QA lead needs no claim to close an unclaimed ticket, nor the reviewer or QA lead to send one back:

```sh
maestro-ticket transition T-12 --from in_review --to done --actor-role qa-lead --actor qa-lead --note "merged <sha>"
maestro-ticket transition T-12 --from in_review --to in_progress --actor reviewer
maestro-ticket comment T-12 --actor reviewer --body-file - <<'END_<8 random letters>'
Kickback: <findings>
END_<the same 8 letters>
```

If someone holds a live claim on the ticket, both moves fail with exit 4 `claimed` until the holder releases it or the lease expires.

**Parked.** Every backlog ticket says why it waits, so no one takes a ticket parked for a plan or a later slice for one held on purpose. `create --status backlog` and `transition --to backlog` need `--parked`: `hold` (someone said wait; a `Hold:` comment names who, why and what lifts it), `deferred` (ready, but cut from the current slice), `unready` (a criterion no command or app can check yet) or `planning` (a planner session took it off the queue to split it). A ticket blocked from backlog keeps its reason and returns with it; `update --parked` changes it; any other move clears it. A ticket that waits on another ticket is not parked: it goes in `todo` with `--deps`, which the store holds until they are done. `list --parked hold,deferred` filters, `list` shows it in STATUS (`backlog:hold`) and `get` on a `parked:` line.

**Goals.** `create --goal <slug>` tags a ticket with the goal it serves (lowercase letters, digits and hyphens); `create --split-from` keeps the old ticket's goal unless `--goal` names another, and `update --goal` sets or clears it. `list --goal` filters. `goals` prints one row per goal with an open ticket (`--all` adds finished ones, `--goal` picks one): counts of done, in review, in progress, todo, blocked and backlog tickets, the total without cancelled ones, and the percent done; `--json` adds the backlog count per parked reason.

**Tiers.** `create --tier junior|senior` says which engineer builds a ticket, so a bot routes a build without reading it: junior for routine work, senior for the rest. A ticket with none reads as senior. `create --split-from` keeps the old ticket's tier unless `--tier` names another; `update --tier` sets it, or clears it with `""`. `list --tier` filters (`senior` includes tickets with none), and `list` shows a `TIER` column. Schema v9 adds the column, empty on every ticket an older store had.

Schema v6 adds `parked` and `goal`. An open backlog ticket, or one blocked from backlog, whose latest comment starts `Parked:` gets `planning`; every other gets `unready`, so the planner reads it before it goes to `todo`, as before; `doctor` fails while a backlog ticket has no known reason. Schema v5 upgrades older stores: tickets in a removed status, or blocked from one, go back to `in_review`, and the old role names map onto current ones; `planner` and `qa-lead` stay (the list is `schemaV5` in `sqlitestore/sqlitestore.go`). Each change is an event with actor `maestro-ticket`. `doctor` fails while any open ticket has an unknown role or status; fix one by moving it to another status with `transition <id> --to <status> --role <role>`, then back. A move to the same status is refused.

**Dependencies and areas.** `create --deps T-1,T-2 --areas tools/maestro-ticket,skills`, or `update <id> --add-deps/--remove-deps/--areas` later. These gate work that writes code: tickets in `todo` or `in_progress`. `claim --next` only hands out such a ticket when its dependencies are all `done` and none of its areas overlaps (equal, or one inside the other) an area of another `todo` or `in_progress` ticket under a live claim. Claiming one by id fails with exit 4 `waiting_on_deps` or `area_busy`; renewing your own lease is exempt. Claims in other statuses (grooming `backlog`, answering `blocked`, review) neither wait nor hold areas. Their holder can't move the ticket into `todo` or `in_progress` without `--release` until the same checks pass, and the holder of a working claim can't `update --areas` onto another live claim's areas. With or without a claim, a ticket can't move from `todo` to `in_progress` while a dependency isn't `done` (exit 4 `waiting_on_deps`). Moving to `done` never waits on dependencies. A cancelled ticket is never `done`, so the store refuses to cancel one that a ticket not yet `done` or `cancelled` depends on (exit 4 `has_dependents`), and refuses a new dependency on a cancelled ticket (exit 2). Areas are repo-relative paths with no `.` or `..` segments, of letters, digits and `. _ - @ +`, compared case-sensitively. A shell would quietly turn any other character into another path (`[id]` is a glob, and zsh reads `(group)` as one), so for such a path, name the folder above it. Cycles are refused.

**Listing.** `list` and `claim --next` order tickets by priority (0 first), then by id as a number (`T-2` before `T-10`), so the first match is the most urgent and the oldest. `list --latest-prefix P` keeps only tickets whose latest comment starts with `P` (for example `Kickback:`); `--not-latest-prefix P` keeps tickets with no comments or whose latest comment doesn't start with `P`. Both match case-sensitively, combine with each other and the other filters, and `--limit` counts after them. The store compares the latest comment's start itself, so a list reads no comment trail. `list` prints no bodies, in `--json` too, as writes don't: `get` prints one, and `list --bodies --json` all of them, for a search. `list --ready` keeps only the tickets `claim --next` could take now: no live claim and, in `todo` or `in_progress`, every dep `done` and no area overlapping a live claim's; with no `--status`, only `todo`, as `claim --next`. A planner hands these out by id without starting a run the claim would refuse.

## Notes that move a ticket

`verdict <id> --holder H --token N --body-file F|- --idempotency-key K` posts a review's or QA's note and makes the move that goes with it, in one call, under the caller's claim. The note's first line picks the move: `Review: GO at <sha>`, `QA: pass at <sha>` and `Rereview: QA at <sha>` post only; `Kickback: <n> blockers at <sha>` and `Kickback: QA fail at <sha>` send the ticket back to `in_progress`; `Escalation: review at <sha>` and `Escalation: QA at <sha>` block it; each move lets the ticket go. It checks the note before it writes: the head's full sha right after the opening words (a review's kickback may say `at none` for a PR that isn't there), a last line `Return-role:` on an escalation, and on a review's kickback that every finding line is a `[blocker` and the count matches, since only a blocker sends a change back ([decisions](../../docs/decisions.md), 22). `handoff <id>` with the same flags posts an engineer's `Handoff:`, whose first line must name the full head sha, moves the ticket to `in_review` and lets it go. Both post the comment first, under the key, then move under `<key>-move`, so the same command again replays; a ticket that moved on without the run gets nothing (`status_conflict`).

`create --lint` refuses an engineer's ship ticket whose body has no numbered criterion or no `Not handled:` line, or that has no `--areas`, naming every gap at once; past six numbered lines it warns on stderr. It refuses a `qa-lead` ticket that isn't a scout titled `Live run:`, and a `designer` ticket that isn't a scout titled `Design:`: `look` hands every such ticket to its job, whose session would refuse it. Other scouts and other roles' tickets pass. The **maestro-create-ticket** skill's create step passes it.

## Cache

`cache restore`, `cache save [--at SHA]` and `cache drop [<name>]` copy the folders an install fills between worktrees, so a fresh worktree doesn't install what another run did for the same lockfile. The list is `## Cache` in the main checkout's `project-setup.md`, never the worktree's copy, which a PR controls: bullets of `<name>: <key file>[, <key file>] -> <folder>`, such as ``- node: `package-lock.json`, `.nvmrc` -> `node_modules` ``. A folder's key is the entry, the platform and the bytes of its key files in this worktree, which must be plain files.

- **`restore`** copies a kept folder in when the worktree has none, by rename from a copy beside it. Anyone may run it.
- **`save`** keeps one, and only when all of these hold: the caller is a `review` or `qa` run; `restore` ran in this worktree before the folder was filled, and the key files haven't changed since (`restore` notes the key in the worktree's git folder, so a merge that moves the lockfile, with the install skipped because the folder is there, keeps nothing under the new key); git sees the checkout as clean, so each cached folder is gitignored; git tracks no file in the folder; no link in it points to an absolute path; and the checkout's tree is the tree of a commit on the main branch, `origin/<main>` as last fetched or the `--at` sha. The key is only the lockfile, so a folder filled while an unmerged change's code ran must reach no other change; once that change is reviewed, tested and merged, what it wrote is what main writes. In practice QA saves, right after its pass merges: its worktree then holds the merge commit's tree.
- **`drop`** removes the kept folders of one name, or of all, so a bad copy goes; the next merge saves anew.

Neither `restore` nor `save` follows a folder or key file whose path runs through a link, at any depth. Copies use `cp -a`, sharing blocks where the filesystem can. The folders sit in `dep-cache/<name>/<key>/` beside the store, and the command touches nothing there it didn't name; a save keeps, per name, the three used last, drops one unused for 14 days, and drops every folder of a name `## Cache` no longer lists (unless a line there failed to parse). A folder, or a copy still being written, is removed by rename first, so no reader finds half of one and no save keeps half of one. With a list to act on, `restore` and `save` exit 0 and print one line per entry (`restored`, `kept`, `miss`, `saved`, `already saved`, `not saved: <why>`, `skipped: <why>`). List only folders that still work after a copy to another path: `node_modules` does, a Python `.venv` does not, and build output depends on source no key file names.

## Slots

`slot [--name checks] [--max 4] [--wait D] -- <command> [args]` runs the command once one of `--max` slots named `--name` is free, so the sessions on one ticket store run at most that many at once, whichever worktree starts them; another repo or clone on the same machine has its own slots. Hundreds of sessions running a heavy check side by side make it slow and flaky under load; wrap that check in `slot` under `## Checks` in `project-setup.md`, such as `maestro-ticket slot --max 4 -- make test`. A slot is a file lock in `slots/` next to the store; the kernel frees it when `slot` exits, however it exits, so a killed run never holds one. The command runs in a process group of its own: on SIGINT, SIGTERM or SIGHUP the whole group gets SIGTERM, then SIGKILL once the command is gone or 5 seconds pass (half a supervisor's grace, so a run's stop kills the group before it kills `slot`), so nothing it started keeps running past its slot (only a SIGKILL of `slot` itself leaves the group running, uncounted, until its run's end kills it). While every slot is busy it prints one line to stderr and waits in line, with no limit unless `--wait` gives one: only the first `--max` live waiters try for a slot, so no waiter is passed by one more than `--max`-1 places behind it, and a waiter that died leaves the line. In a run `launch` started, it marks the wait in `runs/`, so the run's time limit leaves it out (a gap of a minute or more between its touches, as when the VM froze, ends the mark and starts a new one, so frozen time earns no credit), even while the session works on beside a check it put in the background; past it, or stopped while it waits, exit 4 `no_slot`. Otherwise it exits with the command's code: 128 plus the signal for one a signal ended, 127 for a command not found. The command runs with `TMPDIR` set to a folder of its own, `maestro-slot-*` in the temp dir, which `slot` removes when the command ends, pass, fail or signal, read-only files and all; a test runner's temp files (pytest's `pytest-of-<user>`, a numbered folder per run) go with it instead of piling up in the shared temp dir while hundreds of sessions run checks. Before it runs the command, it refuses with `low_disk` as `claim` does. Every flag goes before `--`; after it, each word is the command's. Unix only.

## Exit codes

| Code | Meaning |
|---|---|
| 0 | ok |
| 1 | internal error, or `doctor` found a problem |
| 2 | usage or invalid request, including a disallowed transition (`invalid_transition`), a gate (`forbidden`) or a store made by a newer `maestro-ticket` (`store_too_new`) |
| 3 | not found |
| 4 | conflict: version, `--from`, claimed by another holder, lease lost, idempotency key reuse, `waiting_on_deps`, `area_busy`, `has_dependents`, `stopped` (the kill switch), `busy` (the store stayed locked; try again later), `no_slot` (`slot --wait` ran out), `low_disk` (a filesystem under the free-disk margin, or full) |
| 5 | `claim --next` found no work |

`get` prints every field and the body, but not the whole comment trail: it keeps in full the newest comment of each kind (the first word of its first line, and the second too when that is all letters, so `Kickback: QA` and `Kickback: 2` differ), every `Answer:`, and the newest `Handoff:` and each comment after it, all of them on a ticket with no `Handoff:`. Each other comment prints as its first line, marked trimmed (in `--json`, `"trimmed": true` and `first_line`, with no `body`). `get --full` prints every comment whole. Why: a long trail ran to 60k characters, and sessions read it on every pass. Writes (`create`, `update`, `claim`, `heartbeat`, `release`, `transition`) print the ticket without its body, which the caller wrote or reads with `get`.

Plain `get` sets the ticket body and each comment four spaces in, so a line at the left margin is always the tool's and text can't pass for a later comment: every kind of line break starts an indented line, and any other control character but a tab prints as U+FFFD. Read `--json` for the text as written. With `--json`, errors print `{"error":{"code":"...","message":"..."}}` on stdout.

## Costs

`log-run [--ticket ID]` reads a `claude -p --output-format json` reply on stdin (the last `result` message of `stream-json` too), prints it to stdout unchanged, then records the session's `total_cost_usd` and its tokens summed over `modelUsage`, which counts every model the session called, its subagents included, against the ticket and `--actor`. `launch` does all this for each run it supervises, so bots no longer pipe into it; a run started outside `launch` can (`claude -p ... | maestro-ticket log-run --actor <bot id> --ticket <id>`), with no `--ticket` for a run that works on no one ticket. A resumed session reports its total so far, so each session is one run: logging it again keeps its first actor and its ticket (unless the new log names one), and replaces its totals, unless the new cost is lower, which marks an older reply that came late. An empty or non-JSON reply, which a run that hung or died leaves, exits 2 and records no cost, which is lost; it frees the run's claim, as [Alerts](#alerts) says. A `--ticket` that names no ticket logs the run with none and says so on stderr. `--verbose` replies, a JSON array, work too. Errors go to stderr, never into the reply, and `--json` is refused.

`costs [--by actor|ticket|goal|origin|tries] [--ticket ID] [--since 2026-11-12|72h]` groups the logged runs, most spent first, then a row for all: runs, dollars, share, median per run, then tickets and the median and 90th percentile per ticket. `origin` is who created the ticket, or `split` for one made or linked with `--split-from`; `tries` is its send-backs so far. A run logged on a `cancelled` ticket rewritten as one other ticket counts toward that one, down the chain, in every grouping, so a rewrite or re-file shows the work's whole cost; a ticket split into several keeps its runs, since none of them is its whole work. A second ticket made with `create --split-from` a rewritten ticket makes it such a split, so its runs go back to it. `--ticket` keeps the runs counted toward a ticket and those logged on it. A run with no ticket lands in `(no ticket)` under every grouping but `actor`. `--since` keeps sessions first logged (at the end of their first run) on or after a local date, or within a length of time. The dollars are Claude Code's own estimate at list price, not an invoice. Schema v7 adds the `runs` table; `export` lists it.

`stats costs` splits spend by model, job, why or lean instead, from `stats.db`: see [Run stats](#run-stats).

## Run stats

`stats` (or `stats --help`) lists the views of `stats.db`. They are for people and Claude sessions: with `MAESTRO_TICKET_ACTOR` or `--actor` one of the seven bot ids and no `MAESTRO_RUN_ID`, a bot in its own shell, each refuses with `forbidden` (exit 2), since what a bot reads reaches Grok. A session a bot started has `MAESTRO_RUN_ID` and may read them. A view opens `stats.db` read-only, never makes it, and reads past a writer's lock.

- **`stats case <ticket|run>`** prints a ticket's runs, or one run, oldest first, after a line with their count and spend: a line each with its start, job, model and effort, why it ran, outcome, time, own spend, then what it has of a reason, resume or retry, send-backs, turns, tool calls and fails, a review's verdict and findings (`F1 blocker new`, follow-ups counted), the call it was in when it ended (`open Bash:go 19m`) and its last tool calls (`!` marks a failed one).
- **`stats health`** says whether stats are on, and if off why; the schema, rows, size (with the WAL) and last prune of `stats.db`, or that it is newer, unreadable or not there yet; how many runs on disk ended since its first row and have no row (a write dropped, or a run that started with stats on and ended while they were off), leaving out a command that never started and a run started with stats off; and the store disk's free space and inodes.
- **`stats costs [--by model|job|why|lean] [--since 2026-11-12|72h]`** groups each run's own spend, most first, in the columns `costs` prints, then its tokens. A run's spend is its session's total less the run before it in that session, so a resume counts only what it added; per model, a run is one row per model it used, and the row for all counts it once. The first line counts the runs left out because their spend can't be known: a resume whose session's earlier runs `stats.db` never saw, a run with no result (its stream's tokens carry no dollars) and the run after it in its session, and a run with no model use. `--since` keeps runs started on or after a local date, or within a length of time. It reads detail rows, so the last 90 days at most.

With stats off, or before the first run's end, `case` and `costs` print one line saying so and exit 0.

### Case bundles

`stats bundle --case T-12 [--cost] [--out FILE|DIR]` writes one ticket's runs to a JSON file for maintainers, for a feedback report that names that ticket. Only a person runs it: a bot actor, by `MAESTRO_TICKET_ACTOR` or `--actor`, and any shell with `MAESTRO_RUN_ID` set, a session a bot started included, get `forbidden` (exit 2). It writes `bundle-case-<4 letters>.json` (mode 0600) in `bundles/` beside the store, outside the work tree so no `git add -A` takes it, or in the folder `--out` names, or at the file `--out` names, never over a file that is there, and prints only the file's path, size, sha256 and row counts, and that nothing was sent. Nothing sends it: it leaves the machine only by a person's hand, after the owner reads it and says yes (decision 24). `stats case T-12` shows the same runs. A ticket with no runs in `stats.db` is `not_found` (exit 3); with stats off it prints one line and writes nothing.

The file holds no text, path, session id, ticket or run id, or clock time. Ids become labels, times become offsets, and each name is on its Go list or `other`. Every field has one of the types below; a test holds each bundle struct to them, and the file is checked value by value before it is written.

| Type | Holds | Fields |
|---|---|---|
| Label | `T1` for the case; `R1`, `R2`, ... for its runs, oldest first | `case`, `run`, `resume_of`, `again_of` (a parent outside the case is left out) |
| Offset15m | minutes from the case's first run start, rounded down to 15 | `start_min` |
| Day | whole days from the first run's start to the last run's end | `span_days` |
| Enum | a name on its list in `cli/statsrun.go`, or `other` | `role`, `job`, `model` (family), `effort`, `why`, `tier`, `nudge`, `stop`, `state`, `outcome`, `reason`, `subtype`, `stop_reason`, `head`, `verdict`, `mode`, `stream`, `open_code`, `ring_err`, `os`, `arch`; a tail call's and a step's `code`; a finding's `kind`, `sev`, `action`, `prior` |
| Count | a count or small number | `bundle_schema`, `stats_schema`, `exit`, `tries`, `drops`, `turns`, `tool_calls`, `tool_fails`, `compactions`, `retries`, `subagents`, `escaped`, `v_tier`; a step's `calls`, `fails`; a finding's `fid` (3 for F3), `pass`, `n` |
| Ms | a duration in ms, under 400 days | `wall_ms`, `claude_ms`, `api_ms`, `wait_ms`, `open_ms`; a step's `ms_sum`, `ms_max` |
| Bytes | a size | `prompt_bytes`, `reply_bytes` |
| Pct | 0 to 100 | `disk_free_pct`, `inode_free_pct` |
| Ver | a commit sha of 7 to 40 hex, or digits and dots | `v_maestro` (`install.yaml`'s maestro-sha), `v_claude` |
| bool | | `with_cost`, `lean`, `after_death`, `is_error`, `wait_capped`, `rang`, `tool_at_pin` (the binary was built from `v_maestro`; its own commit stays out), a tail call's `fail` |
| USD, Tokens | only under `cost`, only with `--cost`, since spend shows a team's size and budget | per run: `ctx_peak`; per model family: the run's own `usd` (to the millionth) and `tokens`, as `stats costs` counts them |

A field with no value is left out. Even without `--cost`, a bundle shows how many runs a ticket took, how long they ran and the size of their prompts and replies.

## Flow

`flow [--since 2026-11-12|72h] [--goal G]` reports where the ship tickets that reached `done` spent their time, from the status changes and comments the store already keeps: per stage (`queue` in `todo`, `build` in `in_progress`, `review` and `qa` in `in_review`, split at review's `Review: GO` and at QA's `Rereview:`, with a stay that comes back from `blocked` going on where it left, and `blocked`) the tickets that passed through, the median and 90th percentile per ticket, the total and its share; then the time a ticket spent in those stages before `done`, how many times review and QA sent tickets back (counted from the moves, so a note posted twice counts once), the share that passed both first time, and the three slowest. Time in `backlog` counts nowhere. Read it before and after a change to the flow: it says which stage to speed up next.

## Alerts

`alerts [--stall 20m]` is the planner's first step each look. It frees what dead runs hold, then prints one line per thing that needs someone now, or `alerts: none`:

- `died`: a run `log-run` started reading whose `log-run` process is gone with no result recorded: the box restarted (`restart:` leads the list), or the pipe was killed. It ends the run as `died`, so the next look doesn't say it again. After a restart it also frees a live claim the run's bot holds on the run's ticket, as `release --died` does, unless another run of that bot on that ticket still goes. On the same boot it frees nothing: `log-run` may have died alone while the run goes on, so the lease and its keepalive decide. On Linux and macOS a run is told from a later process with its pid by the boot's id and its start time; elsewhere, and for a run started in another pid namespace such as a container, a restart can't be seen. A step that fails doesn't stop the rest: the report lists it under `errors` and `alerts` exits non-zero.
- `expired`: a lease it freed, as `reap` does.
- `eta missed`: an ETA past due and not met, with what is still open.
- `revived`: a live claim whose lease ran out and came back.
- `stalled`: an `in_review` ticket with no live claim and no change for `--stall`, a handoff no one picked up. `doctor` names these too, as a warning that still passes.

`log-run` records each run as it starts reading (actor, ticket, pid), and `launch`'s supervisor records its run the same way, with its own pid, so `alerts` and `export` see every run, and how it ended: `result`, or `no_result` for an empty or unreadable reply. On `no_result` it frees the run's claim the same way `died` does, and says so on stderr. `export` lists the runs under `launches`.

`eta --goal G --by TIME [--tickets T-1,T-2]` records when the owner was told a goal, or those tickets, would be ready; a second call replaces it, and `--clear` drops it. `--by` takes `21:15` (today), `2026-11-12 21:15`, an RFC 3339 time or a length such as `90m`, and refuses a time already past, as `eta` refuses a goal no ticket has (a misspelt slug would read as met for ever). It is met once each named ticket is `done`, or, with none named, once each of the goal's tickets made by the due time is: work added later is a new promise. A promised ticket that was split stands for the newer tickets its latest `Split into` comment names; a named ticket cancelled with no split was never delivered. Once `alerts` finds an ETA met it stays met, until a new `eta` replaces it. `eta` alone lists each with `met`, `open` or `missed`. Schema v8 adds the `launches` and `etas` tables.

## Look

`look` is the planner bot's look in one call, so the bot spends one step and reads a few lines instead of a dozen listings. It runs what `alerts` runs (a missed ETA becomes a `send chief-of-staff:` line, once per goal and date; died runs, expired and revived leases print as `alert:`, since pickup handles a died run), then sorts every open ticket into the planner's rows, skipping one with a live claim or a live run, a judge run's tickets included, or a job run that ended within `--stall` and isn't acked, since its own pickup routes it, unless its end was left to the planner, whose look answers it, which a board machines share reads from the run's launch (`busy`):

- **Fixed rows become a line to send.** Waiting for review or after a `Rereview:`: `send reviewer: review <id>`. Passed review, or QA not finished: `send qa-lead: qa <id>`. Sent back at TRIES 0 or 1, or stopped with no send-back, unless a dep holds it (as a shared cause's fix does): the engineer who last claimed it (else by tier); a junior's at TRIES 2: the senior. `todo` and ready: by role, then tier: a `Design:` ticket to the designer, a `Live run:` ticket to the QA lead, an engineer's to the junior or senior (none means senior; a junior split already sent back twice goes to the senior); any other role becomes a judge row. Builds stop at `--limit` work runs, counting the `in_progress` tickets with a live claim, the builds handed out lately and the build runs whose session hasn't claimed yet, and work under way gets the free slots before `todo`.
- **Fixed writes it makes itself**, printed as `wrote:`: a ticket parked `planning` whose latest move is over an hour old goes back to `todo`; one sent back 3 or more times goes to `blocked` with `Escalation: build at TRIES <n>:` listing each `Kickback:` and `Return-role: engineer`, then `Sent up: chief of staff:`, and its card goes out as `send chief-of-staff:`; a ready design pickup missed goes up as pickup sends it. Each card is a handout to the chief of staff named by what it sends (the design escalation, the try count), so of looks and pickups at once one sends it, and a ticket's next card isn't held back by its last.
- **The planner's own jobs it starts**, printed as `started:`, each held 6 hours so a run that waits on the chief of staff isn't started again (a failed one frees its ticket): `finish` for a split not closed or an `Escalation:` only `finish` settles (a PR merged outside QA, a split or drop waiting on a dependent); `rule <id>: again` for a blocked ticket whose latest note is an `Answer:`; a rewrite (`plan`) for a senior's ticket sent back twice; `plan fix <id>` for a live run its failure put on hold.
- **The rest become `judge:` rows**, one line of facts each: a block to answer, a ticket back in review after an `Answer:` (`rerun`), a ticket whose runs died twice, a hold, an `unready` or `deferred` ticket whose goal has nothing else in todo, build or review, a `Follow-ups:` ticket once the whole board has nothing in todo, build or review, an urgent follow-up, and three or more tickets blocked or sent back at TRIES 2 or more (`cause`, judged under its own key). `--judge` starts one `job judge` on up to 20 of them, with `rules.md`'s lines as its standing rules (with none, it starts no judge and prints an `error:`), prints `judging: <run> on <n> rows`, and leaves the rest for the next look. A row the judge took is not judged again for 6 hours while its ticket doesn't change (its version, its last update, its latest note); a judge run that fails frees its rows.

It hands builds out by `board.json`'s limit. `--limit <n>` from the planner, as its old block passes it, writes that limit to `board.json` until `rules set limit` takes over, and is then ignored with an `alert:`; anyone else's `--limit` holds for that look only. Stdin given with `--judge`, the old block's memories, seeds `rules.md` the same way until `rules text` takes over, less any line that names `--limit`.

## Standing values

`rules` holds what code reads instead of a bot typing it, beside the store: `board.json` (`limit`, `qa_slots`, who set them and when) and `rules.md` (one rule a line, each ending `(set by <actor>, <date>)`, which code writes). `rules show` prints them; `rules set limit|qa_slots <n>`, `rules text` (the whole list on stdin), `rules add` (lines on stdin) and `rules drop <n>` change them. Each write takes `board.lock` for one read and write, replaces its file whole, and adds a line to `rules.log` (`<time> <actor> <key> <old> -> <new>`; for the rules, a hash of each list). A write refuses inside a run (`MAESTRO_RUN_ID` set), and from a bot other than the planner or the chief of staff (for `qa_slots`, the QA lead or the chief of staff), whether `--actor` or `MAESTRO_TICKET_ACTOR` names it. `doctor` warns while either file is missing.

Each send and start is a handout file in `handouts/` next to the store, one per ticket and bot, made with `O_EXCL`: of looks at once only one sends a job, and none is sent again within `--stall` (20 minutes), so a job on its way to a claim isn't handed out twice. pickup records the jobs it hands out the same way, so a look in the next minutes doesn't send them again. A send whose record the store can't make or read stays in, with a `route:` line saying why, and a chain leaves that run to its launcher's pickup. Records over a day old go. While `maestro/STOP` sits next to the store, or a usage limit holds, it hands out and starts nothing (`stopped:` or `paused:`), though alerts still free what dead runs hold. `--report` adds the report's fixed lines: `progress:` per goal, `runs:`, `stuck:`, `held:` and `sent up:`, each naming 10 tickets at most. The last line counts the board; a board with nothing to do prints only `nothing to do; <counts>`. On a 140-ticket open board it prints about 2,200 chars, where the 14 listings it replaces printed 25,700.
