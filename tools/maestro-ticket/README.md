# maestro-ticket

The maestro ticket store and its CLI. Harness sessions call it to create, claim, move and comment on tickets; the Chief of Staff reads its event log to decide when to wake up. `Backlog.md` is a generated view of it.

Go, single static binary, no cgo (pure-Go SQLite driver).

## Build, test, install

From `tools/maestro-ticket/`:

```sh
go build -o bin/maestro-ticket ./cmd/maestro-ticket   # build
go test ./...                                         # unit, race and multi-process tests
go test -race ./...                                   # same, with the race detector
gofmt -l . && go vet ./...                            # lint
go install ./cmd/maestro-ticket                       # put maestro-ticket on $GOBIN
```

`go test -short ./...` skips the test that spawns 200 processes.

## Where the data lives

`--store PATH`, else `$MAESTRO_TICKET_STORE`, else `$(git rev-parse --git-common-dir)/maestro/tickets.db`. The git common dir is shared by every worktree of a repo and is never committed, so all sessions on all `maestro/` branches see one store and the working tree stays clean. A relative path is taken from the working directory.

Before opening the store, the CLI refuses (exit 2) a bare repo or a submodule when the path comes from git, a store directory on a network or VM/container-share filesystem (NFS, SMB, FUSE, 9p, virtiofs and others), and a directory where file locks don't exclude each other. `doctor` reports these as the `filesystem` and `locks` checks. `MAESTRO_TICKET_ALLOW_UNSAFE_FS=1` overrides the filesystem and lock checks.

`maestro-ticket render` writes `Backlog.md` next to the store (`<git common dir>/maestro/Backlog.md` by default), or to `--out`. It never lands in a work tree, so no agent branch can commit it (F8, decision 0223). It writes a temp file, fsyncs and renames, with `<!-- generated by maestro-ticket render, do not edit -->` on line 1. The output depends only on the store, so re-rendering an unchanged store is a no-op diff.

## Guarantees

- **One writer at a time.** SQLite in WAL mode, `busy_timeout=5000`, `synchronous=NORMAL`, `foreign_keys=ON`. Every write is one `BEGIN IMMEDIATE` transaction: the change and its event commit together or not at all. Readers never block writers.
- **Leases, not locks.** `claim` gives `<bot-id>/<session-id>` a lease for `--ttl` (default 30m, 5s to 24h). One bot can run several sessions, each with its own leases. `heartbeat` extends a live lease; a lease that has expired is lost, and the ticket is claimable again, so a crashed session frees its work without cleanup. `release` is safe to repeat. A claim does not change status.
- **Heartbeats from a background process.** `claim --keepalive PID` starts a detached `keepalive` that heartbeats every TTL/3 while process PID (the harness session, one of yours, not PID 1) lives. It stops by itself when PID exits (the lease then expires) or when the lease is released, lost or re-claimed.
- **Expired leases are reported.** `reap` (or `reap --every 30s` as a background process) frees every expired lease, logs `lease_expired` (actor `maestro-ticket`, data `holder`, `token`, `expired_at`, `expiries`) and adds one to the ticket's `lease_expiries`. Any write to a ticket with an expired lease does the same first, so no expiry goes unlogged. Freeing an expired lease doesn't change `version`.
- **Fencing tokens.** Every claim returns `claim.token`, a lease number that grows on every claim of the ticket, including a holder re-claiming its own lease, and is never reused. `heartbeat` and `release` always need `--holder` and `--token`; on a claimed ticket, so do `transition` and `comment`. Another holder gets exit 4 `claimed` (`lease_lost` for heartbeat), a missing token exit 2, a stale token exit 4 `lease_lost`. A write that names a lease it no longer holds gets `lease_lost` even if nobody holds the ticket now. Releasing a lease that is already gone is a no-op.
- **Optimistic versions.** `claim`, `release` and `transition` bump `version`; `heartbeat` and `comment` don't. `transition --from S --expect-version N` fails with exit 4 if someone else got there first. Moving to `done` or `cancelled` clears the lease.
- **Idempotent retries.** `--idempotency-key K` on `create`, `update`, `claim`, `release`, `transition`, `comment`: a retry with the same key and request returns the first result and writes nothing; the same key with a different request fails with exit 4. Replaying a `claim` key returns the ticket as it is now while that lease is live, and fails with `lease_lost` once it is gone. Failed writes don't use up the key.
- **Append-only events.** Every write appends to `events` (triggers reject update and delete). `seq` only grows, and events commit in seq order, so `events --since N` with the `next_seq` from the last call never misses or repeats one. No new events means nothing changed. `events --since N --wait 10m` blocks until an event after N matches (or the wait ends, with an empty list), so a watcher sleeps without polling.
- **Outbox.** Every event also gets one `outbox` row (`event_id`, `kind`, `payload` = the event as `events --json` prints it, `attempts`, `next_attempt_at`, `delivered_at`) in the same transaction, for a delivery hook. Events from before schema v3 are backfilled as delivered. `doctor` fails if an event has no outbox row.
- **Backups.** `backup [--keep 24] [--every 1h]` writes a checked `VACUUM INTO` snapshot to `backups/` next to the store and prunes older snapshots (only files named like one, never the store); `export` prints the store as one JSON document. To restore, stop writers, copy a snapshot over `tickets.db` and delete `tickets.db-wal` and `tickets.db-shm`. Reset every `events` cursor to the restored store's last seq: a cursor past it sees nothing new until seq catches up.
- **Schema migrations.** `PRAGMA user_version` records the schema. Opening an older store runs each missing step in order, in one transaction; a newer store is refused.

## Workflow

Statuses and allowed moves live in `ticket/ticket.go` (`workflows`), one table per ticket type (`create --type`, default `ship`):

- **ship:** `backlog → todo → in_progress → in_review → in_qa → ready_to_release → done`. Only `--actor-role operations-manager` (or `$MAESTRO_TICKET_ROLE`) sets done.
- **scout:** `backlog → todo → in_progress → in_review → done`. Only the ticket's owner (`create --owner`, default the creator) sets done, as `--actor`.

Both allow send-backs to `in_progress`, `in_progress → todo` (escalation) and `todo → backlog`. Any non-terminal status can go to `blocked` or `cancelled`; `blocked` goes back only to the status it came from (`blocked_from`). `claim --next` never hands out `backlog`; claim those by id. Send-backs from `in_review` or `in_qa` to `in_progress` add one to a ship ticket's `tries`; a scout send-back doesn't count (`0432`).

**Dependencies and areas.** `create --deps T-1,T-2 --areas tools/maestro-ticket,skills`, or `update <id> --add-deps/--remove-deps/--areas` later. These gate work that writes code: tickets in `todo` or `in_progress`. `claim --next` only hands out such a ticket when its dependencies are all `done` and none of its areas overlaps (equal, or one inside the other) an area of another `todo` or `in_progress` ticket under a live claim. Claiming one by id fails with exit 4 `waiting_on_deps` or `area_busy`; renewing your own lease is exempt. Claims in other statuses (grooming `backlog`, answering `blocked`, review, QA, release) neither wait nor hold areas (`0245`). Their holder can't move the ticket into `todo` or `in_progress` without `--release` until the same checks pass, and the holder of a working claim can't `update --areas` onto another live claim's areas (`0243`). Areas are repo-relative paths with no `.` or `..` segments, compared case-sensitively. Cycles are refused. Decisions: `docs/decisions/0200`–`0206`, `0220` onward and `0432`.

## Exit codes

| Code | Meaning |
|---|---|
| 0 | ok |
| 1 | internal error, or `doctor` found a problem |
| 2 | usage or invalid request, including a disallowed transition (`invalid_transition`) or a gate (`forbidden`) |
| 3 | not found |
| 4 | conflict: version, `--from`, claimed by another holder, lease lost, idempotency key reuse, `waiting_on_deps`, `area_busy` |
| 5 | `claim --next` found no work |

With `--json`, errors print `{"error":{"code":"...","message":"..."}}` on stdout.

## Layout

| Path | What |
|---|---|
| `ticket/` | Domain: types, workflow, validation, errors, and the `Store` interface. No storage code. |
| `sqlitestore/` | The SQLite driver. |
| `render/` | `Backlog.md` generation and atomic writes. |
| `envcheck/` | Filesystem and file-lock checks run before opening the store. |
| `cli/` | Flag parsing and output. Talks only to `ticket.Store`, except for opening the store. |
| `cmd/maestro-ticket/` | `main`. |

## Adding a driver

Implement `ticket.Store` (for example on Postgres: `SELECT ... FOR UPDATE SKIP LOCKED` for `ClaimNext`; serialize event inserts, or assign `seq` at commit, so events become visible in seq order). Run the `sqlitestore` tests against it, then select it in `cli.(*call).open`. Nothing else in the CLI changes.
