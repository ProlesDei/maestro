# maestro-ticket

The maestro ticket store and its CLI. People and bots call it to create, claim, move and comment on tickets. `Backlog.md` is a generated view of it.

Go, single static binary, no cgo (pure-Go SQLite driver).

## Build, test, install

From `tools/maestro-ticket/`:

```sh
go build -o bin/maestro-ticket ./cmd/maestro-ticket   # build
go test -race ./...                                   # unit, race and multi-process tests
gofmt -l . && go vet ./...                            # lint
go install ./cmd/maestro-ticket                       # put maestro-ticket on $GOBIN
```

`go test -short ./...` skips the test that spawns 200 processes.

## Where the data lives

`--store PATH`, else `$MAESTRO_TICKET_STORE`, else `$(git rev-parse --git-common-dir)/maestro/tickets.db`. Every worktree of a repo shares the git common dir and git never commits it, so all sessions on all branches see one store and the working tree stays clean. A relative path starts from the working directory.

Before it opens the store, the CLI refuses (exit 2) a bare repo or a submodule when the path comes from git, a store directory on a network or VM/container-share filesystem (NFS, SMB, FUSE, 9p, virtiofs and others), and a directory where file locks don't exclude each other. `doctor` reports these as the `filesystem` and `locks` checks. `MAESTRO_TICKET_ALLOW_UNSAFE_FS=1` overrides both.

`maestro-ticket render` writes `Backlog.md` next to the store, or to `--out`. It never lands in a work tree, so no branch can commit it. It writes a temp file, fsyncs and renames, with `<!-- generated by maestro-ticket render, do not edit -->` on line 1. The output depends only on the store, so re-rendering an unchanged store changes nothing.

## Guarantees

- **One writer at a time.** SQLite in WAL mode, `busy_timeout=5000`, `synchronous=NORMAL`, `foreign_keys=ON`. Every write is one `BEGIN IMMEDIATE` transaction: the change and its event commit together or not at all. Readers never block writers.
- **Leases, not locks.** `claim` gives `<bot-id>/<session-id>` a lease for `--ttl` (default 30m, 5s to 24h). `heartbeat` extends a live lease. An expired lease is lost and the ticket is claimable again, so a crashed session frees its work without cleanup. `release` is safe to repeat. A claim does not change status.
- **Heartbeats from a background process.** `claim --keepalive PID` starts a detached `keepalive` that heartbeats every TTL/3 while process PID (one of yours, not PID 1) lives. It stops when PID exits or turns zombie (the lease then expires) or when the lease is released, lost or re-claimed. `claim` and `keepalive` refuse with exit 2 their own PID, or a PID in their session when that session has no terminal: Claude Code, Codex and Grok Build run each command that way, so that PID (the shell, `$$`, or a wrapper such as `timeout`) exits with the command. Pass the shell's parent, the harness. From a terminal, `$$` is your login shell and is accepted. The check relies on that: a harness that gives each command a terminal (Codex can) lets a wrong `$$` through, and one that runs commands in its own session with no terminal gets even `$PPID` refused.
- **Expired leases are logged.** `reap` frees every expired lease, logs `lease_expired` (actor `maestro-ticket`, data `holder`, `token`, `expired_at`, `expiries`), adds one to the ticket's `lease_expiries` and checkpoints the WAL. Any write to a ticket with an expired lease does the same first, so no expiry goes unlogged. Freeing an expired lease doesn't change `version`.
- **Fencing tokens.** Every claim returns `claim.token`, a lease number that grows on every claim of the ticket, re-claims included, and is never reused. `heartbeat` and `release` always need `--holder` and `--token`; on a claimed ticket, so do `transition` and `comment`. Another holder gets exit 4 `claimed` (`lease_lost` for heartbeat), a missing token exit 2, a stale token exit 4 `lease_lost`. A write that names a lease it no longer holds gets `lease_lost` even if nobody holds the ticket now. On an unclaimed ticket, `transition` and `comment` need neither flag.
- **Optimistic versions.** `claim`, `release` and `transition` bump `version`; `heartbeat` and `comment` don't. `transition --from S --expect-version N` fails with exit 4 if someone else got there first. Moving to `done` or `cancelled` clears the lease.
- **Idempotent retries.** `--idempotency-key K` on `create`, `update`, `claim`, `release`, `transition`, `comment`: a retry with the same key and request returns the first result and writes nothing; the same key with a different request fails with exit 4. Replaying a `claim` key returns the ticket as it is now while that lease is live, and fails with `lease_lost` once it is gone. Failed writes don't use up the key.
- **Append-only events.** Every write appends to `events` (triggers reject update and delete). `seq` only grows, and events commit in seq order, so `events --since N` with the `next_seq` from the last call never misses or repeats one.
- **Backups.** `backup [--keep 24]` writes a checked `VACUUM INTO` snapshot to `backups/` next to the store and prunes older snapshots (only files named like one, never the store). `export` prints the store as one JSON document. To restore, stop writers, copy a snapshot over `tickets.db` and delete `tickets.db-wal` and `tickets.db-shm`. Then reset every `events` cursor to the restored store's last seq.
- **Schema migrations.** `PRAGMA user_version` records the schema. Opening an older store runs each missing step in order, in one transaction; a newer store is refused.

## Roles and workflow

Roles: `chief-of-staff`, `planner`, `engineer`, `qa-lead`, `reviewer`. The QA lead records results as a comment starting `QA: pass` or `QA: fail`; there is no QA status. `create --role`, `claim --role`, `transition --role` and `--actor-role` refuse any other name (exit 2).

Statuses and moves live in `ticket/ticket.go` (`workflows`), one table per ticket type (`create --type`, default `ship`):

- **ship:** `backlog → todo → in_progress → in_review → done`. Only `--actor-role reviewer` (or `$MAESTRO_TICKET_ROLE=reviewer`) sets done.
- **scout:** `backlog → todo → in_progress → in_review → done`. Only the ticket's owner (`create --owner`, default the creator) sets done, as `--actor`.

Both allow `in_review → in_progress` (send-back), `in_progress → todo` (escalation) and `todo → backlog`. Any non-terminal status can go to `blocked` or `cancelled`; `blocked` goes back only to the status it came from (`blocked_from`). `claim --next` never hands out `backlog`; claim those by id. A send-back adds one to a ship ticket's `tries`; a scout send-back doesn't.

The reviewer needs no claim to close or send back an unclaimed ticket:

```sh
maestro-ticket transition T-12 --from in_review --to done --actor-role reviewer --actor reviewer --note "merged <sha>"
maestro-ticket transition T-12 --from in_review --to in_progress --actor reviewer
maestro-ticket comment T-12 --actor reviewer --body "Kickback: <findings>"
```

If someone holds a live claim on the ticket, both moves fail with exit 4 `claimed` until the holder releases it or the lease expires.

Schema v5 upgrades older stores: tickets in a removed status, or blocked from one, go back to `in_review`, and the old role names map onto current ones; `planner` and `qa-lead` stay (the list is `schemaV5` in `sqlitestore/sqlitestore.go`). Each change is an event with actor `maestro-ticket`. `doctor` fails while any open ticket has an unknown role or status; fix one by moving it to another status with `transition <id> --to <status> --role <role>`, then back. A move to the same status is refused.

**Dependencies and areas.** `create --deps T-1,T-2 --areas tools/maestro-ticket,skills`, or `update <id> --add-deps/--remove-deps/--areas` later. These gate work that writes code: tickets in `todo` or `in_progress`. `claim --next` only hands out such a ticket when its dependencies are all `done` and none of its areas overlaps (equal, or one inside the other) an area of another `todo` or `in_progress` ticket under a live claim. Claiming one by id fails with exit 4 `waiting_on_deps` or `area_busy`; renewing your own lease is exempt. Claims in other statuses (grooming `backlog`, answering `blocked`, review) neither wait nor hold areas. Their holder can't move the ticket into `todo` or `in_progress` without `--release` until the same checks pass, and the holder of a working claim can't `update --areas` onto another live claim's areas. Areas are repo-relative paths with no `.` or `..` segments, compared case-sensitively. Cycles are refused.

**Listing.** `list` and `claim --next` order tickets by priority (0 first), then by id as a number (`T-2` before `T-10`), so the first match is the most urgent and the oldest. `list --latest-prefix P` keeps only tickets whose latest comment starts with `P` (for example `Kickback:`); `--not-latest-prefix P` keeps tickets with no comments or whose latest comment doesn't start with `P`. Both match case-sensitively, combine with each other and the other filters, and `--limit` counts after them.

## Exit codes

| Code | Meaning |
|---|---|
| 0 | ok |
| 1 | internal error, or `doctor` found a problem |
| 2 | usage or invalid request, including a disallowed transition (`invalid_transition`) or a gate (`forbidden`) |
| 3 | not found |
| 4 | conflict: version, `--from`, claimed by another holder, lease lost, idempotency key reuse, `waiting_on_deps`, `area_busy` |
| 5 | `claim --next` found no work |

With `--json`, errors print `{"error":{"code":"...","message":"..."}}` on stdout.

## Layout

| Path | What |
|---|---|
| `ticket/` | Domain: types, roles, workflow, validation, errors, and the `Store` interface. No storage code. |
| `sqlitestore/` | The SQLite driver. |
| `render/` | `Backlog.md` generation and atomic writes. |
| `envcheck/` | Filesystem and file-lock checks run before opening the store. |
| `cli/` | Flag parsing and output. Talks only to `ticket.Store`, except for opening the store. |
| `cmd/maestro-ticket/` | `main`. |

## Adding a driver

Implement `ticket.Store` (for example on Postgres: `SELECT ... FOR UPDATE SKIP LOCKED` for `ClaimNext`; serialize event inserts, or assign `seq` at commit, so events become visible in seq order). Run the `sqlitestore` tests against it, then select it in `cli.(*call).open`. Nothing else in the CLI changes.
