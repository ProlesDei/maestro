# maestro-ticket

The maestro ticket store and its CLI. People and bots call it to create, claim, move and comment on tickets. `Backlog.md` is a generated view of it.

Go, single static binary, no cgo (pure-Go SQLite driver).

## Build, test, install

From `tools/maestro-ticket/`:

```sh
go build -o bin/maestro-ticket ./cmd/maestro-ticket   # build
go test -race ./...                                   # unit, race and multi-process tests
gofmt -l . && go vet ./...                            # lint
go install ./cmd/maestro-ticket                       # put maestro-ticket on $GOBIN
```

`go test -short ./...` skips the test that spawns 200 processes.

## Where the data lives

`--store PATH`, else `$MAESTRO_TICKET_STORE`, else `$(git rev-parse --git-common-dir)/maestro/tickets.db`. Every worktree of a repo shares the git common dir and git never commits it, so all sessions on all branches see one store and the working tree stays clean. A relative `--store` starts from the working directory; a relative `$MAESTRO_TICKET_STORE` is refused, since each worktree would read it as its own store. The git default needs git 2.31 or later, and refuses Maestro's own clone in `.maestro/src/`, which would make a second, empty store. It opens only a store that exists: a separate clone of the repo has its own git common dir, so every command there but `doctor` exits 2 `no ticket store` instead of making an empty one. `doctor`, which `install.sh apply` runs, makes the store.

Before it opens the store, the CLI refuses (exit 2) a bare repo or a submodule when the path comes from git, a store directory on a network or VM/container-share filesystem (NFS, SMB, FUSE, 9p, virtiofs and others), and a directory where file locks don't exclude each other. `doctor` reports these as the `filesystem` and `locks` checks. `MAESTRO_TICKET_ALLOW_UNSAFE_FS=1` overrides both.

`maestro-ticket render` writes `Backlog.md` next to the store, or to `--out`. It never lands in a work tree, so no branch can commit it. It writes a temp file, fsyncs and renames, with `<!-- generated by maestro-ticket render, do not edit -->` on line 1. The output depends only on the store and on which leases have run out, so re-rendering an unchanged store changes nothing but a claim that turned `(expired)`.

## Guarantees

- **One writer at a time.** SQLite in WAL mode, `busy_timeout=5000`, `synchronous=NORMAL`, `foreign_keys=ON`. Every write is one `BEGIN IMMEDIATE` transaction: the change and its event commit together or not at all. Readers never block writers.
- **Leases, not locks.** `claim` gives `<bot-id>/<session-id>` a lease for `--ttl` (default 30m, 5s to 24h). `heartbeat` renews the lease to `--ttl` from now (default 30m) and never cuts a longer one short. An expired lease is lost and the ticket is claimable again, so a crashed session frees its work without cleanup. Until someone writes to the ticket, though, the holder's heartbeat revives it and logs `lease_revived`: a machine that slept past the lease keeps its work, since every write frees an expired lease first and every claim takes a new token. It stays lost if another claim took one of its areas meanwhile. `release` is safe to repeat; `release --died` frees the lease of a run that hung or died and adds one to `lease_expiries`, as an expiry would. A claim does not change status.
- **Kill switch.** While a file named `STOP` sits next to the store (`<git common dir>/maestro/STOP` by default), every `claim` fails with exit 4 `stopped`, its message starting `refused:`, and no lease that ran out comes back. `list --ready` still lists.
- **Heartbeats from a background process.** `claim --keepalive PID` starts a detached `keepalive` that heartbeats every TTL/3 while process PID (one of yours, not PID 1) lives. It stops when PID exits or turns zombie (the lease then expires) or when the lease is released, lost or re-claimed. `claim` and `keepalive` refuse with exit 2 their own PID, or a PID in their session when that session has no terminal: Claude Code, Codex and Grok Build run each command that way, so that PID (the shell, `$$`, or a wrapper such as `timeout`) exits with the command. Pass the shell's parent, the harness. From a terminal, `$$` is your login shell and is accepted. The check relies on that: a harness that gives each command a terminal (Codex can) lets a wrong `$$` through, and one that runs commands in its own session with no terminal gets even `$PPID` refused.
- **Expired leases are logged.** `reap` frees every expired lease, logs `lease_expired` (actor `maestro-ticket`, data `holder`, `token`, `expired_at`, `expiries`), adds one to the ticket's `lease_expiries` and checkpoints the WAL. Any write to a ticket with an expired lease does the same first, so no expiry goes unlogged. Freeing an expired lease doesn't change `version`.
- **Fencing tokens.** Every claim returns `claim.token`, a lease number that grows on every claim of the ticket, re-claims included, and is never reused. `heartbeat` and `release` always need `--holder` and `--token`; on a claimed ticket, so do `transition` and `comment`. Another holder gets exit 4 `claimed` (`lease_lost` for heartbeat), a missing token exit 2, a stale token exit 4 `lease_lost`. A write that names a lease it no longer holds gets `lease_lost` even if nobody holds the ticket now. On an unclaimed ticket, `transition` and `comment` need neither flag.
- **Optimistic versions.** `claim`, `release` and `transition` bump `version`; `heartbeat` and `comment` don't. `transition --from S --expect-version N` fails with exit 4 if someone else got there first. Moving to `done` or `cancelled` clears the lease.
- **Idempotent retries.** `--idempotency-key K` on `create`, `update`, `claim`, `release`, `transition`, `comment`: a retry with the same key and request returns the first result and writes nothing; the same key with a different request fails with exit 4. For `update`, `transition` and `comment` the lease token isn't part of the request, so a session that claimed again retries under its new token; a `release` names one lease, so its token is. Replaying a `claim` key returns the ticket as it is now while that lease is live, and fails with `lease_lost` once it is gone. Replaying a `create` key returns the ticket as it is now, and fails with exit 4 once it is cancelled. Failed writes don't use up the key.
- **Append-only events.** Every write appends to `events` (triggers reject update and delete). `seq` only grows, and events commit in seq order, so `events --since N` with the `next_seq` from the last call never misses or repeats one.
- **Backups.** `backup [--keep 24]` writes a checked `VACUUM INTO` snapshot to `backups/` next to the store (through `<name>.partial`, so a crash never leaves a part-written file under a snapshot's name) and prunes older snapshots (only files named like one, never the store) and any `.partial` an hour old. `export` prints the store as one JSON document. To restore, stop writers, `maestro-ticket keepalive` processes too, copy a snapshot over `tickets.db` and delete `tickets.db-wal` and `tickets.db-shm`. Then reset every `events` cursor to the restored store's last seq. Ticket ids made after the snapshot come out again, so a `maestro/<id>` branch or PR from then names another ticket now: rename or close it first.
- **Schema migrations.** `PRAGMA user_version` records the schema. Opening an older store first snapshots it to `backups/<store name>-pre-schema-v<n>.db`, such as `tickets-pre-schema-v1.db` (once; `backup --keep` never prunes it), then runs each missing step in order, in one transaction. A newer store is refused with exit 2 `store_too_new`: rebuild `maestro-ticket` from the newest Maestro on the machine.

## Roles and workflow

Roles: `chief-of-staff`, `planner`, `engineer`, `qa-lead`, `reviewer`. Review comes first and QA last, both in `in_review`: the reviewer records a pass as a comment starting `Review: GO`, and the QA lead a pass as one starting `QA: pass`; there is no QA status. `create --role`, `claim --role`, `transition --role` and `--actor-role` refuse any other name (exit 2).

Statuses and moves live in `ticket/ticket.go` (`workflows`), one table per ticket type (`create --type`, default `ship`):

- **ship:** `backlog → todo → in_progress → in_review → done`. Only `--actor-role qa-lead` (or `$MAESTRO_TICKET_ROLE=qa-lead`) sets done, once QA passed and merged the PR, or `--actor-role planner` when the PR merged outside QA.
- **scout:** `backlog → todo → in_progress → in_review → done`. Only the ticket's owner (`create --owner`, default the creator) sets done, as `--actor`.

Both allow `in_review → in_progress` (send-back), `in_progress → todo` (escalation) and `todo → backlog`. Any non-terminal status can go to `blocked` or `cancelled`; `blocked` goes back only to the status it came from (`blocked_from`). `claim --next` never hands out `backlog`; claim those by id. A send-back adds one to a ship ticket's `tries`; a scout send-back doesn't. `create --split-from <id>` starts the new ticket at that ticket's `tries`, so a split or rewrite keeps the count.

The QA lead needs no claim to close an unclaimed ticket, nor the reviewer or QA lead to send one back:

```sh
maestro-ticket transition T-12 --from in_review --to done --actor-role qa-lead --actor qa-lead --note "merged <sha>"
maestro-ticket transition T-12 --from in_review --to in_progress --actor reviewer
maestro-ticket comment T-12 --actor reviewer --body-file - <<'END_<8 random letters>'
Kickback: <findings>
END_<the same 8 letters>
```

If someone holds a live claim on the ticket, both moves fail with exit 4 `claimed` until the holder releases it or the lease expires.

**Parked.** Every backlog ticket says why it waits, so no one takes a ticket parked for a plan or a later slice for one held on purpose. `create --status backlog` and `transition --to backlog` need `--parked`: `hold` (someone said wait; a `Hold:` comment names who, why and what lifts it), `deferred` (ready, but cut from the current slice), `unready` (a criterion no command or app can check yet) or `planning` (a planner session took it off the queue to split it). A ticket blocked from backlog keeps its reason and returns with it; `update --parked` changes it; any other move clears it. A ticket that waits on another ticket is not parked: it goes in `todo` with `--deps`, which the store holds until they are done. `list --parked hold,deferred` filters, `list` shows it in STATUS (`backlog:hold`) and `get` on a `parked:` line.

**Goals.** `create --goal <slug>` tags a ticket with the goal it serves (lowercase letters, digits and hyphens); `create --split-from` keeps the old ticket's goal unless `--goal` names another, and `update --goal` sets or clears it. `list --goal` filters. `goals` prints one row per goal with an open ticket (`--all` adds finished ones, `--goal` picks one): counts of done, in review, in progress, todo, blocked and backlog tickets, the total without cancelled ones, and the percent done; `--json` adds the backlog count per parked reason.

Schema v6 adds `parked` and `goal`. An open backlog ticket, or one blocked from backlog, whose latest comment starts `Parked:` gets `planning`; every other gets `unready`, so the planner reads it before it goes to `todo`, as before; `doctor` fails while a backlog ticket has no known reason. Schema v5 upgrades older stores: tickets in a removed status, or blocked from one, go back to `in_review`, and the old role names map onto current ones; `planner` and `qa-lead` stay (the list is `schemaV5` in `sqlitestore/sqlitestore.go`). Each change is an event with actor `maestro-ticket`. `doctor` fails while any open ticket has an unknown role or status; fix one by moving it to another status with `transition <id> --to <status> --role <role>`, then back. A move to the same status is refused.

**Dependencies and areas.** `create --deps T-1,T-2 --areas tools/maestro-ticket,skills`, or `update <id> --add-deps/--remove-deps/--areas` later. These gate work that writes code: tickets in `todo` or `in_progress`. `claim --next` only hands out such a ticket when its dependencies are all `done` and none of its areas overlaps (equal, or one inside the other) an area of another `todo` or `in_progress` ticket under a live claim. Claiming one by id fails with exit 4 `waiting_on_deps` or `area_busy`; renewing your own lease is exempt. Claims in other statuses (grooming `backlog`, answering `blocked`, review) neither wait nor hold areas. Their holder can't move the ticket into `todo` or `in_progress` without `--release` until the same checks pass, and the holder of a working claim can't `update --areas` onto another live claim's areas. With or without a claim, a ticket can't move from `todo` to `in_progress` while a dependency isn't `done` (exit 4 `waiting_on_deps`). Moving to `done` never waits on dependencies. A cancelled ticket is never `done`, so the store refuses to cancel one that a ticket not yet `done` or `cancelled` depends on (exit 4 `has_dependents`), and refuses a new dependency on a cancelled ticket (exit 2). Areas are repo-relative paths with no `.` or `..` segments, of letters, digits and `. _ - @ +`, compared case-sensitively. A shell would quietly turn any other character into another path (`[id]` is a glob, and zsh reads `(group)` as one), so for such a path, name the folder above it. Cycles are refused.

**Listing.** `list` and `claim --next` order tickets by priority (0 first), then by id as a number (`T-2` before `T-10`), so the first match is the most urgent and the oldest. `list --latest-prefix P` keeps only tickets whose latest comment starts with `P` (for example `Kickback:`); `--not-latest-prefix P` keeps tickets with no comments or whose latest comment doesn't start with `P`. Both match case-sensitively, combine with each other and the other filters, and `--limit` counts after them. `list --ready` keeps only the tickets `claim --next` could take now: no live claim and, in `todo` or `in_progress`, every dep `done` and no area overlapping a live claim's; with no `--status`, only `todo`, as `claim --next`. A planner hands these out by id without starting a run the claim would refuse.

## Slots

`slot [--name checks] [--max 4] [--wait D] -- <command> [args]` runs the command once one of `--max` slots named `--name` is free, so one machine runs at most that many at once, whichever session or worktree starts them. Hundreds of sessions running a heavy check side by side make it slow and flaky under load; wrap that check in `slot` under `## Checks` in `project-setup.md`, such as `maestro-ticket slot --max 4 -- make test`. A slot is a file lock in `slots/` next to the store; the kernel frees it when `slot` exits, however it exits, so a killed run never holds one (a command that outlives a killed `slot` no longer counts). While every slot is busy it prints one line to stderr and waits, with no limit unless `--wait` gives one; past it, exit 4 `no_slot`. Otherwise it exits with the command's code (128 plus the signal for one a signal ended), and passes SIGINT and SIGTERM on as SIGTERM. Every flag goes before `--`; after it, each word is the command's. Unix only.

## Exit codes

| Code | Meaning |
|---|---|
| 0 | ok |
| 1 | internal error, or `doctor` found a problem |
| 2 | usage or invalid request, including a disallowed transition (`invalid_transition`), a gate (`forbidden`) or a store made by a newer `maestro-ticket` (`store_too_new`) |
| 3 | not found |
| 4 | conflict: version, `--from`, claimed by another holder, lease lost, idempotency key reuse, `waiting_on_deps`, `area_busy`, `has_dependents`, `stopped` (the kill switch), `busy` (the store stayed locked; try again later), `no_slot` (`slot --wait` ran out) |
| 5 | `claim --next` found no work |

Plain `get` sets the ticket body and each comment four spaces in, so a line at the left margin is always the tool's and text can't pass for a later comment: every kind of line break starts an indented line, and any other control character but a tab prints as U+FFFD. Read `--json` for the text as written. With `--json`, errors print `{"error":{"code":"...","message":"..."}}` on stdout.

## Layout

| Path | What |
|---|---|
| `ticket/` | Domain: types, roles, workflow, validation, errors, and the `Store` interface. No storage code. |
| `sqlitestore/` | The SQLite driver. |
| `render/` | `Backlog.md` generation and atomic writes. |
| `envcheck/` | Filesystem and file-lock checks run before opening the store. |
| `cli/` | Flag parsing and output. Talks only to `ticket.Store`, except for opening the store. |
| `cmd/maestro-ticket/` | `main`. |

## Adding a driver

Implement `ticket.Store` (for example on Postgres: `SELECT ... FOR UPDATE SKIP LOCKED` for `ClaimNext`; serialize event inserts, or assign `seq` at commit, so events become visible in seq order). Run the `sqlitestore` tests against it, then select it in `cli.(*call).open`. Nothing else in the CLI changes.
